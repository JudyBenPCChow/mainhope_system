## 問題

經過檢查報告（L1–L15）、兩輪審閱、對抗模擬（ADV-1～10）、A1a/A1b/A2 階段切分後，我們累積了約 25 個待處理項、四輪文件往返。這讓我回到最基本的問題：

> **學年鎖這個功能，解決的問題值不值得它創造的成本？**

---

## 學年鎖現在實際做什麼

| 角色 | 規則 | 效果 |
| --- | --- | --- |
| alien | 永不鎖 | — |
| admin | 可編「目前＋下一」學年 | 歷史學年全鎖 |
| teacher | ≥ `26SM` 地板 ∩ 目前＋下一 | 歷史學年全鎖 |

觸及範圍：點名儲存、請假、繳費、排程CRUD、補堂、一對一預約、校曆休課、老師檔期、班別編輯——大約 40+ 個 UI 和 service 掛鉤點。

---

## 它要防的是什麼？

一個場景：**用戶選了舊學年／舊日期，改了不該改的歷史資料，自己沒發現。**

這是「誤操作防護」，不是安全機制：
- 不是防惡意（無 DB 層 RLS，純前端/service assert）
- 不是防權限越界（已有角色 RLS 獨立運作）
- 不是合規要求（我未見文檔中有審計強制鎖定已結算學年的規定）

## 如果完全拿掉學年鎖

### 不會消失的保護

| 保護層 | 狀態 | 說明 |
| --- | --- | --- |
| 角色 RLS | 仍在 | teacher 只能改自己班、不能取消課堂、不能刪 attendance |
| 審計軌跡 | 仍在 | `mgmt_audit_log` 記錄誰改過什麼 |
| UI 自然默認 | 仍在 | 點名／排程／繳費預設顯示當期資料，到歷史需要**主動導航** |
| 寫入 confirm | 可加上 | 若日期／學年非當期 → confirm dialog「你正在修改 `2526` 資料，確定嗎？」 |

### 拿掉會消失的

| 現有東西 | 消失後果 |
| --- | --- |
| 黃色警報橫幅 | 不再嚇到查舊紀錄的行政 |
| 控件全 disabled | 歷史頁面可正常互動 |
| 寫入 guard 拋錯 | admin 可直接修正任何學年的錯帳 |
| L1–L15 全數 | 零工程成本 |
| cutoff 維護 | 不再需要 |
| 過渡窗／遷移寬限爭論 | 不再需要 |
| 雙軌分叉風險 | 不再存在 |

## 關鍵風險評估

### 風險 1：老師誤改歷史點名

- 老師必須**主動導航**到舊日期 → 舊班級 → 點名頁 → 修改狀態 → 儲存
- 這不是「誤觸」——中間有四層主動選擇
- 對比：今日點名頁一打開就能改，那才是誤觸場景
- RLS 保證老師只能改自己班的

**判斷**：風險極低。不是需要系統硬鎖的級別。

### 風險 2：admin 誤改歷史資料

- admin 權限本就幾乎萬能（可改任何班、任何學生）
- 如果 admin 在歷史頁面誤操作，一個輕量 confirm dialog（「你正在修改 `2526` 學年資料」）比鎖死整個頁面更精準
- 對比：現況是為了防這件低概率事，把所有 admin 的歷史查閱體驗都犧牲了

**判斷**：低風險，可輕量化解，不值得硬鎖。

### 風險 3：無合規／審計強制鎖定

- 如果有的話，那是外部約束，沒得商量
- 目前文檔（`ACADEMIC_YEARS.md`、稽核報告、角色政策）中沒有提到任何審計或合規要求強制鎖定已結算學年
- 學年鎖是團隊自行設計的防禦機制，不是外部強制的

**判斷**：若無外部約束，這是純產品取捨。

## 輕量替代方案

若拿掉學年鎖，但仍想保留基本誤操作防護：

1. **非當期 confirm dialog**：寫入操作若目標學年 ≠ 目前學年，彈 confirm「你正在修改 `2526` 學年資料，確定要儲存嗎？」——精準、不打擾瀏覽、無需維護 cutoff。
2. **審計標記**：在 `mgmt_audit_log` 中標記「非當期學年操作」，方便日後追溯。
3. **保留 RLS**：不做任何改動——teacher 的底線保護仍在。

三項加起來的工程成本 ≈ 拿掉現有 guard 呼叫 + 加一個 confirm dialog wrapper，遠低於 A1+A2。

---

## 我的建議

**請產品負責人明確回答**：

1. 有沒有外部審計／合規要求強制鎖定已結算學年？（有 → 必須做，沒得討論）
2. 如果沒有：學年鎖的「誤操作防護」價值，是否高於上述所有成本＋UX 代價？
3. 如果答案是「不值」：是否接受用「非當期 confirm dialog + audit log + RLS」取代現有學年鎖？

技術上，拿掉學年鎖是**零風險**的——因為現有 RLS 和 P0-1 等角色限制提供了底線保護。拿掉只會讓系統更簡單、行政更少阻礙、工程更少維護。
