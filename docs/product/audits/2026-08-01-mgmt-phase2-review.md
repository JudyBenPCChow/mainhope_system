## 整體評價

這份計劃的思維框架是對的：以管理層真正要回答的問題為中心，而非功能清單。KPI placeholder 的診斷精準（七個問題全部屬實），決策佇列的概念有實際價值，「交行政跟進」的窄寫入設計聰明。但計劃的規模、優先序和依賴鏈有根本性問題，需要重新檢視。

## 🔴 核心質疑（5 項）

### 1. 營運規模 vs 自建計糧引擎的合理性

**現實數據**：seed data 顯示 8 名教師、50 名學生、40 個班。計糧規則文檔確認約 20 人（含 8 名 PT 專科、6 名功課班、2 名固定月薪、2 名分成制、2 名獨立定價、1 名 WFH）。

**問題**：為 20 人自建一個支援 6 種薪酬模式、跨角色加總、MPF、月結 snapshot、版本化費率的計糧引擎，工程成本極高，但受惠人數極少。

**對比**：
- 市場產品（TutorCruncher、Teachworks、Classcard）是 SaaS，有全職團隊維護
- 香港市面上有專門的計糧軟件／MPF 申報方案
- 以這個規模，Excel + 人手核對的錯誤率可能比軟件 bug 更低

**不是說不要做**，而是應該明確回答：為什麼不用現成工具？如果答案是「需要與 attendance/schedule 資料深度整合」，那至少要承認這是一個高成本決定，並在 Wave 0 先做一個**極簡版**（例如只做 PT 專科 HC 制，覆蓋 8 人）驗證可行性，而非一次過做全部 6 種模式。

---

### 2. 依賴鏈阻塞：計糧引擎有三層未滿足的前置條件

計劃 Wave 2（計糧）依賴以下項目，**全部未完成**：

| 前置條件 | 現狀 | 影響 |
|---|---|---|
| `substitute-teacher-reporting` | backlog `open`，未開工 | 代堂薪酬歸屬錯誤（歸主責老師而非當日老師），計糧基礎數據不可信 |
| `PAYROLL_RULES.md` 納入 repo | 僅存在於 `~/Desk/`，未複製到 `docs/playbooks/frontdesk/` | 規則未版本化，開發時可能引用過期版本 |
| 功課班／WFH 工時輸入機制 | 不存在（計劃說「先由 manager/alien 輸入或匯入」） | 等於要先做一個工時 UI 或 CSV import 功能 |
| 薪酬設定 schema | 不存在（目前只有 `salary_per_lesson` 單一欄位，且 seed 值全為 $260） | 需從零設計多模式費率表、有效日期、snapshot 機制 |
| 學費收入 per class 計算 | `sumConsumedLessonValue()` 存在但未接入 dashboard | Mark/Christine/Cyndi 的分成制依賴每班學費數據 |

**結論**：Wave 2 不可能在這些前置條件完成前啟動。而這些前置條件分散在 backlog 各處（代堂歸屬、工時 UI、學費計算），沒有統一的推進計劃。

---

### 3. Wave 0 是巨型瓶頸

Wave 0 的 scope 包含：

- KPI 字典（需與 stakeholders 反覆確認商業定義）
- 修正所有 placeholder 目標
- 修正 `subjectIds` 篩選（query 未實際套用）
- 加入學年 selector（目前 dashboard filter 完全沒有）
- 接入 `sumConsumedLessonValue()`
- 呈現 `statusBuckets`（數據已取回但畫面沒顯示）
- 拆 `is_mgmt_reader()`／`is_mgmt_writer()`（跨 22+ migration files）

這**每一項**都是非平凡的改動。學年 selector 需要改 filter bar UI、filter type、query 邏輯、以及所有 KPI 的區間計算。RLS 拆分需要 retrofitting 22+ migration 檔案。KPI 字典需要與 Mark/Christine 就每個 KPI 的商業定義達成共識 — 這不是 engineering 工作，是 product 工作。

**如果 Wave 0 卡住，Wave 1-4 全部無法啟動。**建議把 Wave 0 拆成 0a（KPI 字典與資料完整度，純規格）和 0b（實作修正），並考慮把部分項目（如 RLS 拆分）推到更後。

---

### 4. 決策佇列的訊噪比問題

計劃提出 7 大類別自動產生的 `MgmtDecisionItem`。但以 50 名學生的規模：

- 「今日需決定」大部分日子可能只有 0-3 項
- 續費提醒在正規學年每月只有一批（月費週期）
- 催繳在暑期不適用
- 班別健康變化慢（一週看一次就夠）

**風險**：
- 如果大部分日子決策佇列接近空白，首頁會顯得空虛，manager 可能養成不看的習慣
- 如果為了填充而降低閾值，會產生大量噪音，同樣訓練 manager 忽略
- 「5 分鐘決策駕駛艙」的預設是每天都有值得關注的事 — 對 50 人補習社未必成立

**建議**：先手動追蹤一個月，記錄 Mark/Christine 實際上做了哪些「管理決定」，再反推哪些應該自動化。不要預先假設 7 個類別都需要。

---

### 5. Wave 優先序值得商榷

當前排序：KPI地基 → 首頁 → 計糧 → 續費催繳漏斗 → 班別資源

**質疑**：計糧（Wave 2）為什麼排在續費／催繳（Wave 3）之前？

- 從 manager 的「四個健康摘要」來看，現金與學生排在人員之前
- 續費／催繳直接影響現金流，是營運生命線
- 計糧一個月做一次；續費催繳是持續性問題
- 計糧的工程風險遠高於續費催繳

建議排序：
1. KPI 地基（精簡版）
2. 首頁 + 決策佇列（先做續費／催繳／出席三類）
3. 續費／催繳／漏斗（完整版）
4. 計糧（先做 PT 專科 HC 制 MVP，再加其他模式）
5. 班別資源 + 教師運作

## 🟡 建議檢討（7 項）

### 6. 首頁與 MgmtDashboard 的資料一致性

計劃說首頁放精簡摘要、`/MgmtDashboard` 保留完整分析。但兩者共用同一批 KPI 數據來源（`mgmtDashboardQueries`）。如果 Wave 0 修正了 placeholder 目標、接入 `sumConsumedLessonValue`、加入學年 selector，兩邊的數字必須一致。

**風險**：首頁和完整版用不同 query 或不同過濾條件，導致同一 KPI 顯示不同數字。需要明確：首頁是完整版的**缓存子集**還是**獨立 query**？

---

### 7. 「已賺取學費」的數據質量問題

計劃大量依賴 `sumConsumedLessonValue()`（已賺取學費 = 實際已上堂且可計費的堂次價值）。但：

- 出席紀錄的完整性取決於 admin 有點名
- 目前低出席警示仍是 placeholder（未接上實際數據）
- 如果點名不完整，已賺取學費會被低估
- 「收入漏洞對帳」（Wave 3）正是要找出這類問題

**這形成一個循環依賴**：要用已賺取學費做 KPI，但已賺取學費的準確性依賴 attendance 品質，而 attendance 品質問題要到 Wave 3 才系統化偵測。

**建議**：在 Wave 0 先做一個「數據完整度儀表板」（已報讀無收款、已上堂無點名、已排程無報讀），這比 KPI 字典更能立即改善數據品質。計劃在 Wave 3 才做的收入漏洞對帳，其實應該是 Wave 0 的基礎建設。

---

### 8. 計糧規則中的模糊邊界

審查 `~/Desk/計糧系統規則說明.md` 後發現以下邊界需要在實作前澄清：

| 問題 | 影響 |
|---|---|
| Christine 功課班抽成條件「≥12 人」— 是報讀人數還是出席人數？只計功課班還是全部學生？ | 觸發條件不明確，$800 的差別 |
| 「其他（未單獨列名）」功課班教師 $100/hr — 這些人如何進入系統？需要為未知教師建 placeholder？ | schema 設計問題 |
| Mark 的全公司 override 是每月固定還是不定？如果他某月完全沒教班，仍抽 10%？ | 規則文檔說「任何月份」，但邏輯上需確認 |
| Sum 的 1on1/1on2 固定價 vs PT 專科班的 3HC/4HC 轉換 — 兩者互斥，但系統如何區分 Sum 的 1on1 和 PT 導師的 1on1？ | 需要 class 或 schedule 上有標記 |
| 功課班工時 — 如何知道 Leo 做了 20 小時功課班而非 20 小時專科？ | 需 schedule 上有 class kind 區分 |
| 費率變更的 effective date — 如果月中改費率，是整月用新費率還是按日拆分？ | 規則文檔沒說，但月結時必須有答案 |

---

### 9. RLS 拆分的實際成本

計劃要求拆 `is_mgmt_reader()` 和 `is_mgmt_writer()`。目前 `is_mgmt_staff()` 被 22+ migration files 引用。改動範圍：

- 所有 RLS policy 的 `using` 和 `with check` 子句
- 每個 policy 需要決定：這個操作是 reader 還是 writer？
- 有些操作難以二分（例如 manager 可以看繳費紀錄但不能改 — 是 reader 但需要 access payment 表）

**建議**：不要追求一次性全拆。先拆「薪酬相關」的 policy（約 3-5 個），其他維持 `is_mgmt_staff()` 並標已知債。

---

### 10. 現有 `salary_per_lesson` 欄位的過渡

目前 `teachers_private` 有 `salary_per_lesson` 欄位（seed 值全為 $260）。新計糧系統引入多模式費率表後，這個欄位如何處理？

- 廢棄？保留作 fallback？
- 如果保留，與新費率表的同步問題？
- Migration 需要處理數據遷移

---

### 11. 與 backlog 其他項目的衝突

Backlog 中有多個進行中或待開工項目，與第二期計劃存在潛在衝突：

| Backlog 項目 | 狀態 | 與第二期的關係 |
|---|---|---|
| 流動裝置介面 | `in_progress` | 第二期首頁「手機優先」— 需要等 mobile wave 完成嗎？ |
| 正規逾期罰款／禁止入室 | `open` 高優先 | 第二期 Wave 3 才做催繳 — 但這是高優先、政策已有、只欠實作 |
| 代堂算薪／出勤報表 | `open` 中優先 | **阻塞計糧 Wave 2** — 必須先完成 |

特別注意：**逾期罰款是目前 backlog 中唯一高優先的 open 項目**，政策文檔已有，只欠系統實作。它被排在 Wave 3，但直覺上它比計糧更迫切（直接影響現金流）。

---

### 12. 市場研究引用的恰當性

計劃引用 TutorCruncher、Teachworks、Classcard 並說「只採納兩個原則」。但這些產品的核心價值不在個別功能，而在**整合** — schedule → attendance → billing → payroll 的資料流是他們的競爭壁壘。

明學的現狀是：這些模組的數據品質參差（出席未完整點名、學費計算有 placeholder、漏斗混用不同 cohort）。在整合之前，先確保每個模組的數據是可信的，可能比加一個決策層更重要。

## 🟢 做得好的地方

1. **KPI placeholder 診斷精準**：七個問題全部從程式庫驗證屬實（hardcoded 目標、subjectIds 未套用、statusBuckets 未展示、無學年 selector、sumConsumedLessonValue 未接入、低出席為空 placeholder、逾期用 payment_date 而非第 2/3 堂規則）

2. **首頁／營運總覽分離**：`MgmtHomeView`（決策駕駛艙）vs `MgmtDashboardView`（深入分析）的分工正確解決了目前兩者內容重複的問題

3. **「交行政跟進」窄寫入**：給 manager 有限的操作能力（檢視／暫緩／交行政），不改動核心營運數據。這是聰明的權限設計

4. **計糧 snapshot 設計**：月結後保存 snapshot、日後費率不可改寫歷史 — 審計意識正確

5. **排除清單明確**：不做成績／知識點、不做多校區／AI、不做完整會計／HR、不做「淨利潤」— 防止 scope creep

6. **驗收標準具體可測**：每個驗收項目都可以客觀判斷通過與否（不是「系統性能良好」這類空洞標準）

7. **正規／暑期分流意識**：續費、催繳、漏斗都把正規學年和暑期分開處理，避免季節性雜訊

8. **`no show` 語義區分**：扣堂 vs 實際出席使用不同定義，避免把沒來但已扣堂的學生誤標為出席異常

## 📋 總結

| 類別 | 數量 | 關鍵項 |
|---|---|---|
| 🔴 核心質疑 | 5 | 規模 vs 自建計糧、三層未滿足前置條件、Wave 0 巨型瓶頸、決策佇列訊噪比、計糧 vs 續費的優先序 |

**一句話總結**：計劃的診斷是對的（KPI 有 placeholder、dashboard 需要學年 selector、manager 需要決策輔助），但處方過重。以 50 學生 8 教師的規模，與其花三個月建一個支援 6 種薪酬模式的計糧引擎，不如先用 Excel 計糧，把工程資源集中在**數據完整度**（讓 KPI 可信）和**續費催繳**（直接影響現金流）。建議把計糧從 Wave 2 推到 Wave 4，先做一個 MVP（只做 PT 專科 HC 制）驗證可行性。
