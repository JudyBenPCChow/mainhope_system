# 計糧 UI：模擬後仍須補強的審計缺口

> 日期：2026-08-01  
> 前提：假設 [`2026-08-01-payroll-finance-ui-review.md`](2026-08-01-payroll-finance-ui-review.md) 的 §6 建議已全數實作  
> 對照：兩份 Cody 模擬報告（[`2026-08-01-payroll-cody-finance-audit-simulation.md`](2026-08-01-payroll-cody-finance-audit-simulation.md)、[`2026-08-01-payroll-cody-finance-audit-simulation-gpt56.md`](2026-08-01-payroll-cody-finance-audit-simulation-gpt56.md)）  
> 方法：逐項檢查模擬中提出的困難，判斷 UI 審查的改善建議是否**真正解決**了該困難。解決了的剔走，仍不足的寫入本檔。

## 判斷標準

Cody 在「無人可問、出錯扣獎金」下要能回答五題才算安心提交（取自 GPT-56 結論）：

1. 這是 7 月哪一個版本、資料截止至何時？
2. 所有應出糧的人是否已在名單內？
3. 每一節是否真的可計薪，且人頭／班型／當日老師正確？
4. 每種公式的輸入值、原價、費率及例外是否可追溯？
5. 所有調整、排除和未完成項目是否明確由 Mark 接手承擔？

以下按這五題組織。每題下列出「UI 審查已做」和「仍不足」兩層。

## 1. 版本與資料截止時間

### UI 審查已做
- §1.1 月結齊備度（未點名堂數、缺費率人數、Cody 工時狀態）
- §2.6 重算摘要

### 仍不足

| # | 缺口 | 來源 | 嚴重 |
|---|---|---|---|
| 1.1 | **無資料截止時間戳記**。Cody 看到一份數字但不知道這些數據是「截至何時」的。如果有人在 Cody 審到一半補點名，Cody 無法判斷自己審的是不是最終版。 | GPT-56 #4 | 🔴 |
| 1.2 | **重算後只有摘要，無逐節 diff**。UI 審查 §2.6 寫「顯示重算摘要（金額變動人數、新增未點名等）」。但 Cody 需要知道**哪些人、哪些節、哪個欄位（HC／費率／代堂歸屬／班型）變了、金額差多少**。摘要級（「3 人金額變動」）不足以證明自己沒漏。 | GPT-56 #10 | 🔴 |
| 1.3 | **缺少「版本」概念**。Cody 今天看的數字和昨天看的是否同一版？如果沒有 version identifier，無法在 audit log 中追溯「Cody 審的是 v3，但提交的是 v4」。 | GPT-56 #21 | 🟡 |

### 建議

``` 
頁面頂部加一行：
「資料截至 2026-08-03 14:00｜計算版本 #3（8/3 重算）｜前版 #2（8/1 初算）→ 查看差異」

重算後彈出 diff 模態：
「本次重算影響 3 人 5 節：
  • Natalie Kwok — S4 中文班 8/12 節：HC 3→4，+$70
  • Liam Lai — S2 數學班 8/15 節：代堂歸屬更正（Kenneth→Liam），+$290
  • Cody Cheong — WFH 工時已補：+$600
  以上已自動更新至當前版本。」
```

### UI 審查已做
- §1.1 月結齊備度
- §1.4 逐人已審

### 仍不足

| # | 缺口 | 來源 | 嚴重 |
|---|---|---|---|
| 2.1 | **齊備清單只檢查「已在名單內的人」，不檢查「名單是否漏了人」**。Cody 看到 17 人的工資單，但指南列了 20+ 人。Cheryl Ng 沒出現 — 是她本月真的無堂，還是 query 漏了她？Cody 無法分辨。 | GPT-56 #5, sim1 #14 | 🔴 |

```
└─────────────────────────────────────────────┘

跨模式教師（Leo、Judy）的展開明細需分區塊顯示：
  Leo Chan
  ├─ PT 專科班（一般費率）  $360  [展開看 2 節明細]
  └─ 功課班 $70/hr        $1,400  [展開看 20hr 明細]
  合計：$1,760
```

## 3. 逐節可計薪證據鏈

### UI 審查已做
- §1.5 分成原價池
- §1.6 代堂進出摘要
- §1.8 異常 deep-link
- §2.4 公式速查
- §3.6 1on1 等價人頭說明

### 仍不足

| # | 缺口 | 來源 | 嚴重 |
|---|---|---|---|
| 3.1 | **分成制看不到「原價時點」**。UI 審查 §1.5 展示原價池合計，但沒說明這個原價是**課堂發生當日的 course price** 還是**今天的 course price**。如果 7 月某班原價 $3,200，8 月加了價變成 $3,500，用今天的價去計 7 月糧就會出錯。Cody 需要確認 system 拿的是歷史價。 | GPT-56 #13 | 🔴 |
| 3.2 | **科目分類沒有正式欄位**。Mark 的 10% 只計數學／M1／M2；Christine 的 10% 只計中國語文（排除中國歷史、中國文學）。如果 class 的 subject 欄位是自由文本或人手標籤，可能出現「Maths」「數學」「Mathematics」等 variant，query 可能漏計或多計。Cody 需要在分成明細中看到**哪些節被判入 pool、哪些被排除、排除原因是什麼**（例如「中國歷史 — 不屬中國語文 pool」）。 | GPT-56 #12 | 🔴 |
| 3.3 | **1on1/1on2 班型沒有歷史快照**。UI 審查 §3.6 會顯示等價人頭，但沒說明系統用的是**課堂當日的班型**還是**當前班型**。一個 1on2 班如果月中有一個學生退讀，後半個月變成 1on1，7 月上半的節應用 1on2（4HC），下半應用 1on1（3HC）。如果系統用當前班型（1on1）去計全月，上半月會被少計。Cody 需要看到逐節的「當日班型快照」。 | GPT-56 #14 | 🔴 |
| 3.4 | **每位學生的扣堂狀態不可見**。指南規定：現場、錄影、Zoom、no show、毋須補回的請假會計入；病假、事假不計。Cody 要核對某節的 HC 數，不能只看「出席人數」，必須看到每位學生的**當日狀態**（出席／合資格缺席／不合資格缺席／no show）及其是否計入薪酬 HC。目前 UI 只有 attendance 的 head count 數字，沒有 per-student 明細。 | GPT-56 #7 | 🔴 |
| 3.5 | **補堂／試堂／取消的薪酬歸屬無事件時間線**。指南對這些情況有規定，但 UI 沒有逐節顯示「這是原訂課還是補堂？學生何時請假？何時安排補堂？老師是否實際到場？」。Cody 需要節級事件時間線才能判斷一節是否該計薪。 | GPT-56 #8 | 🟡 |
| 3.6 | **MPF band 的計算步驟不透明**。UI 審查 §4 評為「可接受」，但 GPT-56 #17 明確指出 Cody 需要看到：適用薪酬→落入哪個 band→僱員供款→僱主供款，四步分開顯示。只有最終扣款數字不足以核對（例如無法分辨「$0 是因為低於 $7,100 所以僱員免供，還是系統漏計」）。 | GPT-56 #17, sim1 #8 | 🟡 |
| 3.7 | **波動異常缺少逐節對照**。UI 審查 §2.1 加了較上月 %，但 sim1 #12 指出只看 % 不夠。Cody 需要看到「是哪幾節導致了變化」— 是課堂真的少了，還是漏計？沒有上月逐節並排對照，Cody 無法證明。 | sim1 #12 | 🟡 |

### 建議

```
每節 LessonCard 展開後顯示：

┌─────────────────────────────────────────────┐
│ 8/12 S4 中文班（Christine Fan）              │
│ 班型：小組（當日快照）· 科目：中國語文         │
│ 原價：$4,000（2026-07 生效版本）              │
│                                             │
│ 學生出勤（HC 計薪 = 4）：                    │
│  • 陳大明 — 出席 ✅ 計入                      │
│  • 李小美 — no show ✅ 計入（已扣堂）          │
│  • 張小華 — 病假 ❌ 不計入                    │
│  • 黃小強 — 出席 ✅ 計入                      │
│  • 林小芬 — 出席 ✅ 計入                      │
│                                             │
│ 計法：分成制 60%                             │
│  個人教學：$4,000 × 60% = $2,400             │

│                                             │
```

## 4. 公式輸入值與費率追溯

### UI 審查已做
- §2.4 公式速查
- §2.2 缺費率異常類型

### 仍不足

| # | 缺口 | 來源 | 嚴重 |
|---|---|---|---|
| 4.1 | **固定月薪缺少「適用月份證據」**。Sophie 和 Katie 公式極簡，但 Cody 仍需確認 7 月是否整月適用該月薪、是否曾調薪／停職／無薪假。UI 顯示 $16,000 但沒附「此月薪自 2026-01-01 生效，至 2026-07-31 仍為最新」的證明。 | GPT-56 #15 | 🟡 |
| 4.2 | **費率變更的 effective_date 追溯**。如果 Natalie 的初中 HC 費率 8 月 1 日從 $120/$60 加到 $130/$70，Cody 在審 7 月糧時必須看到系統用了舊費率而非新費率。目前 UI 沒顯示「7 月各節套用的費率版本」。 | GPT-56 #13 延伸 | 🟡 |

### 建議

```
固定月薪教師展開顯示：
  Sophie Lau — 固定月薪 $16,000
  適用期間：2026-01-01 起（無結束日）
  本月狀態：全月在職 · 無調薪 · 無無薪假
  → 本月薪酬：$16,000

每節 HC 制明細附費率註腳：
  $150 + $70 × (4-1) = $360
  費率來源：高中一般 PT（$150/$70），自 2026-01-01 生效
```

## 5. 調整、排除與責任移交

### UI 審查已做
- §1.3 硬阻擋改「排除後提交」
- §1.7 人手調整全鏈（財務→管理層核准）
- §2.7 提交確認摘要
- §2.8 結算後更正

### 仍不足

| # | 缺口 | 來源 | 嚴重 |
|---|---|---|---|
| 5.1 | **Cody 工時的職責分離未強制**。UI 審查 §1.2 有狀態機（未報／已報待核准／已核准），但沒說**誰可以核准**。Cody 不應能核准自己的工時。系統必須阻擋：Cody 提交工時後，只能由 manager（Mark/Christine）核准。如果 Cody 同時持有 manager 角色，系統應至少彈出「你正在核准自己的工時，建議由另一管理層覆核」警告。 | GPT-56 #16 | 🔴 |
| 5.2 | **「已審」是點擊，不是可驗證聲明**。UI 審查 §1.4 加了逐人已審勾選。但 GPT-56 #21 指出勾選本身不構成審計紀錄。每次標記已審時，應記錄：審核人、時間、當時的計算版本號、審核範圍（全審／只審總額／跳過哪些項）及例外說明。純 checkbox 在爭議時無法證明 Cody「真的有審」。 | GPT-56 #21 | 🔴 |
| 5.3 | **管理層核實頁若只看摘要，無法真正覆核**。UI 審查 §1.7 提到管理層核准佇列，但沒說明 Mark 的核實頁面應該展示什麼。Mark 不應只看到「總薪酬 $58,230，財務 Cody 已審」就按核准。他需要對風險項（未點名已排除、代堂歸屬、分成原價、人手調整、Cody 工時）有**強制抽查**。例如：系統隨機選 3 個風險項，要求 Mark 展開確認後才能核准。 | GPT-56 #23 | 🟡 |
| 5.4 | **提交後異常清單被清空造成假安全感**。UI 審查 §2.8 有結算後更正，但沒說結算後異常是否仍可見。如果提交後異常列表清空，Cody 可能誤以為「本月已無問題」，但實際上只是「狀態已凍結、待辦被隱藏」。未點名但已被排除的節，應持續顯示在「已排除待跟進」區塊，直到有人處理。 | sim1 #11 | 🟡 |
| 5.5 | **已審完成 ≠ 所有異常已處理的區別不明**。Cody 可以逐人勾選「已審」但仍有未點名節未被處理（只是被標記）。提交前必須明確區分：「已審核無異常」「已審核有異常但已知悉」「未審」。目前 UI 審查只有「已審」checkbox，缺少異常處理狀態的獨立追蹤。 | GPT-56 #22 | 🟡 |
| 5.6 | **CSV 沒有版本控制**。UI 審查 §2.5 把 CSV 分對帳用和銀行用，但沒說 CSV 本身要帶版本 metadata。Cody 下載了 CSV，三天後 Mark 問「你傳給銀行的是哪一版？」— Cody 無法證明。CSV 檔名和表頭應含：月份、計算版本號、匯出時間、匯出人、hash。 | GPT-56 #24 | 🟡 |

### 建議

```
提交前確認對話框：

┌─────────────────────────────────────────┐
│          提交 2026 年 7 月計糧           │

│      處理：已排除該節，Natalie 本月$290   │
│      責任移交：Mark Yu（將跟進補點名）     │
│    • 本月缺 Cody WFH 時數（尚未提交）     │
│                                         │
│  ⚠ 管理層需抽查：3 項                    │
│    • Mark Yu 分成原價池（系統抽查）       │
│    • Liam Lai 代堂歸屬（系統抽查）        │
│    • Cody 工時核准（系統抽查）            │
│                                         │

│  ☐ 本人（Cody Cheong）確認已核對全部 17   │
```

## 總結：缺口一覽

| 嚴重 | 數量 | 項目 |
|---|---|---|
| 🔴 必須補 | 9 | 資料截止時間、重算逐節 diff、母名單含 $0、跨模式拆分、原價時點、科目分類正式欄位、班型歷史快照、per-student 扣堂狀態、Cody 職責分離、已審審計紀錄 |
| 🟡 應補 | 9 | 版本 identifier、補堂事件時間線、MPF band 步驟、波動逐節對照、月薪適用證據、費率版本追溯、管理層抽查、異常持續可見、CSV 版本控制 |

**核心結論**：UI 審查已把「操作流程」打通了（齊備→審核→調整→提交）。仍不足的是**證據鏈的深度** — 每個數字背後的原價版本、班型快照、扣堂判定、費率適用期間，Cody 都需要看到「證明」，而非僅僅看到「結果」。

這不是 UI 加幾個區塊能解決的。部分項目（如原價時點、班型快照）需要確保**數據層**在計薪時 freeze 了歷史值，而非拿當前值動態計算。這已經超出 UI 範疇，是計糧引擎的設計問題。
