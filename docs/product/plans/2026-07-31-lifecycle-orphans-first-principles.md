## 原目標（第一性錨點）

**觸發個案（林藝涵）**：取消 7/24 請假＋7/25 補堂後，點名紙無名，但 `attendance_details` 仍有 7/25 兩堂，且仍計入已上堂數。

**問題定義**：

> **孤兒**＝上游「應到／資格」已不存在，但下游事實列仍在，且仍影響已上堂數／對帳。

**已定原則**：

- 不靜默刪計費出席
- 資格變更會產孤兒 → 攔截＋Confirm
- 行政可單列刪（admin＋稽核）
- 真上課保留 vs 誤點／取消補堂 → 顯式清理

**本檔要問的**：現行方案（階段 A 攔截＋三路 Confirm＋eligibility／audit／rollcall 等）會否**偏離或削弱**上述原目標？下列七點是團隊自查；請顧問逐項 Agree／Disagree／改寫，並給優先級。

---

## 判決（團隊暫見，請挑戰）

方案**能解林藝涵「下次再取消」**，也補了誤刪／寫回縫；但相對「資格沒了就不該再扣堂」，最大張力是：

1. 「保留出席」會**合法重現**原 bug  
2. 攔截**不治**既有錯帳  
3. 計費仍**不理資格**，其他入口仍產同病  

若要緊貼原目標，成功條件應先釘死：取消補堂後預設清可刪列且已上堂數對、現有個案有修復通道、計費或健康檢查至少一層能抓「無資格仍計費」——其餘當護欄排程。

## 偏離／削弱點

### FP-1：「保留出席」等於允許原 bug 再現

**現象**：Confirm 三路含「只改請假／調堂、**保留**出席（明示將成孤兒／已上堂數仍計）」。

**與原目標張力**：原痛點正是「點名紙無名、已上堂數仍＋」。此路會**刻意造出同款孤兒**。階段 B 的 O0（資格已結束標籤）未上線前，職員選錯後幾乎無法在 UI 發現。

**第一性問題**：若營運共識是「取消補堂＝通常不應再扣堂」，常見案是否應**預設一併清**或對「保留」加高摩擦（二次 Confirm／僅 admin／必須填原因），而非與「一併刪」對等三路？

| 選項 | 含義 |
| --- | --- |
| A | 維持對等三路（現方案） |
| B | 預設一併刪；「保留」僅 admin 或須填原因 |
| C | 取消請假路徑**禁止**保留；真要留上課事實改走 O2／事後工具 |
| D | 其他（請寫） |

---

### FP-2：攔截只防未來，不治現況

**現象**：方案主軸是資格變更時掃描＋Confirm。林藝涵**已存在**的出席列、以及任何歷史「保留」／漏路徑孤兒，階段 A 仍靠手工 SQL；O2（admin 單列刪）又卡在 RPC／真權限就緒。

**與原目標張力**：若目標含「把錯的已上堂數改對」，只做攔截＝**預防器，不是修復器**。觸發個案本身在 A 上線當日仍可能未解。

**第一性問題**：階段 A 是否必須附帶**最小修復通道**（例如：O2 在 RPC 前用受限 service＋mgmt RLS／既有 delete helper；或個案 runbook 升級為「驗收必清現況」）？

| 選項 | 含義 |
| --- | --- |
| A | A 只預防；現況繼續 SQL（現方案傾向） |
| B | A 必須含可用的 admin 單列刪（即使 RPC 未全就緒，定義清楚的過渡） |
| C | A 驗收含「林藝涵型現況列已清」作為人工／腳本門檻，與功能分開 |
| D | 其他 |

---

### FP-3：根因未動，旁路仍會再產孤兒

**現象**：已上堂數主路徑仍只看出席 status 白名單（`isBillableAttendanceStatus`），**不看**當前應到資格。階段 A 封的是請假／調堂／試堂／點名寫回等入口；盤點中同樣標「高」的清報讀、軟／硬取消排程、退讀等在 B／C。

**與原目標張力**：問題定義是「資格與事實脫鉤仍計費」；A 修的是**幾條寫入／撤銷入口**，不是計費定義。上線後易誤以為「孤兒問題做完了」，同病從別條路再現。

**第一性問題**：原目標的「完成」應以哪條為準？

| 選項 | 含義 |
| --- | --- |
| A | 入口攔截足夠（計費維持現狀；O5 後期抓漏）— 現方案 |
| B | 計費或報表層加「無資格不計／或標註」才算對齊定義（範圍明顯變大） |
| C | A 上線溝通必須寫明「只覆蓋取消補堂主路徑」；完成定義＝林藝涵路徑＋文件，不宣稱全盤 |
| D | 其他 |

---

### FP-4：掃描錨在「舊 makeup」，不是「無資格的出席」

**現象**：可刪列＝舊 `makeup_schedule_id` 宿主／peers 出席 − eligibility（enrollment ∪ trial ∪ otherMakeup）。刻意不掃請假日原班出席；`schedule_id IS NULL`、歷史保留列、漏攔截 API 不進 O1。

**與原目標張力**：真孤兒定義是「無應到仍有列」。O1 是**路徑近似**，對林藝涵夠用，但不是完整定義 → 洞靠 O2／O5。

**第一性問題**：是否接受「O1＝取消補堂專用近似；完整 orphan＝O5」的分工？還是 A 就要更靠近定義（例如變更後重算該生該日／該班無資格列）？

| 選項 | 含義 |
| --- | --- |
| A | 接受路徑近似；O5 補定義（現方案） |
| B | A 起掃描改為「變更後該生在相關 schedule 上無資格的出席」 |
| C | 其他 |

---

### FP-5：範圍膨脹延遲止血

**現象**：原優先是對齊林藝涵。現行定案綁 O1-audit 拋錯、樂觀鎖、peers、eligibility、type／disposition、O1t、O1-rollcall、O2 權限門檻等。多為防回歸，但任一項拉長＝觸發個案繼續靠 SQL。

**與原目標張力**：最小可驗證成功應是「取消已點名補堂 → 一併刪 → 已上堂數對」。護欄若變成「全部定案／一次做完才動手」的隱性門檻，會削弱止血。

**第一性問題**：階段 A 可否切「必做／可隨後」而不降低對林藝涵的正確性？

| 選項 | 含義 |
| --- | --- |
| A | 維持現階段 A 全套再動手（現方案） |
| B | 最小切片：O1（含 eligibility）＋audit＋文件；rollcall／O1t／O2 明確標「A2」可隔週 |
| C | 其他（請列必做清單） |

### FP-6：老師路徑與行政路徑政策不一致

**現象**：行政三路 Confirm；老師請假精靈遇已點名補堂 → **失敗**（含姓名＋請假 id），無「一併刪／保留」。

**與原目標張力**：同一業務（清調堂）兩套結果。可能正確（老師不應刪計費事實），但未寫「失敗後標準作業」時，營運會卡關或私下 SQL。

**第一性問題**：失敗後是否必須有文件化 SOP（轉 admin／O2）才算對齊「不靜默、可收尾」？

| 選項 | 含義 |
| --- | --- |
| A | 維持老師失敗；O6 寫清轉交 admin（現方案可補文件） |
| B | 老師亦可「一併刪」（權限／誤刪風險上升） |
| C | 老師可「保留」但不能刪出席 |
| D | 其他 |

---

### FP-7：「一併刪」不可逆

**現象**：本期不加 `attendance_details.deleted_at`；Confirm 後硬刪。誤點只能重點名或 DB 備援。

**與原目標張力**：與「勿靜默刪」不邏輯矛盾，但與「計費事實很貴」並存時，缺還原是產品風險。

**第一性問題**：階段 A 是否接受硬刪＋清晰 Confirm，還是刪計費列必須 soft-delete／可還原？

| 選項 | 含義 |
| --- | --- |
| A | 接受硬刪（現方案） |
| B | 刪計費列改 soft-delete（範圍變大，原鐵律「本期不加 deleted_at」需翻案） |
| C | 硬刪但 Confirm 對計費列二次確認 |
| D | 其他 |
