## 總評

這份第一性檢查的品質比對抗模擬更高——它不問「方案有沒有 bug」，而是問「方案還是不是在解原問題」。七個張力點中，FP-1 和 FP-3 是真正的架構性問題，FP-5 是務實的排程問題。其餘四個可以在現有框架內解決。

## FP-1：「保留出席」等於允許原 bug 再現

**判決**：Agree — 這是對原目標的偏離，但是**有意為之的產品取捨**，不是設計失誤。

**理由**：原痛點「點名紙無名但已上堂數仍＋」的前提是**行政不知道**。三路 Confirm 的「保留出席」路徑讓行政**明知且主動選擇**保留。本質不同。

但 FP-1 問的對：在 O0 未上線的階段 A–B 期間，選錯的後果確實無法在 UI 發現。問題不是「要不要保留選項」，而是「保留選項的摩擦是否足夠防止誤選」。

**建議**：**選項 B 的變體** — 保留三路但調整預設權重：

- 取消請假：預設鍵＝一併刪；保留出席＝二次 Confirm 或需選原因（「學生確實出席」）
- 退讀（O4）：預設鍵＝保留出席（與方案一致）
- 文案對「保留」鍵加 ⚠️ 前綴：「⚠️ 保留出席（將脫離資格，仍計入已上堂數）」

不要拿掉保留選項（選項 C）——模擬 3 的場景（學生真有來補堂、行政誤取消請假）是真實存在的。

**優先級**：P1 — 開工前寫入方案 UX 規範，不改架構。

## FP-2：攔截只防未來，不治現況

**判決**：Agree — 這是對原目標的覆蓋缺口。方案是預防器，不是修復器。

**理由**：觸發個案（林藝涵）在階段 A 上線當日仍需手動 SQL。如果「解決林藝涵個案」是階段 A 的隱含驗收條件，那方案目前不滿足。

**建議**：**選項 C** — 階段 A 驗收條件加入「林藝涵型現況列已透過人工／腳本清理」，與功能程式碼分開。做法：

1. 階段 A 上線前，用 backlog 提供的 SELECT 清查 production 現有孤兒
2. 人工確認後逐筆刪除（或跑一次性 script，但需 audit）
3. 階段 A 驗收清單加一條：「production 現有 attendance 孤兒已清理」

同時，O2（admin 單列刪）拖到 RPC 就緒確實太慢。建議過渡方案：在 RPC 完成前，O2 用現有 mgmt RLS（已知非真 Auth）+ `deleteAttendanceStatusForSchedule` 包一層含 audit 的 service 函式，只開給 admin role（前端仍 assert `mgmtRole`，但文件寫明這是過渡、RPC 就緒後替換）。風險可接受——現況 admin 本來就能透過 Table Editor 刪。

**優先級**：P1 — 驗收條件補入方案；過渡 O2 視團隊對 RPC 時程的判斷。

## FP-3：根因未動，旁路仍會再產孤兒

**判決**：Agree — 這是最根本的張力，但**不是本方案該解的**。

**理由**：計費定義（status 白名單不看資格）是系統層級的設計決策，改它會牽動整個 billing/payment 模組。本方案的正確定位是**攔截已知入口**，不是改革計費引擎。

**建議**：**選項 C** — 溝通必須精確。階段 A 上線時的文件／公告必須寫明：

> 此版本覆蓋：取消補堂／清調堂／試堂取消時，自動偵測並可一併清理孤兒出席。  
> 尚未覆蓋：退讀、軟取消排程、清報讀等入口（後續版本）。  
> 計費定義維持現狀（status 白名單）；O5 健康檢查上線前，孤兒仍可能從未攔截路徑產生。

這是溝通紀律問題，不是技術問題。

**優先級**：P1 — 寫入 O6 文件。

## FP-4：掃描錨在「舊 makeup」，不是「無資格的出席」

**判決**：Partial — 同意這是路徑近似而非完整定義，但**這是正確的分工**。

**理由**：這在審閱 #01 P0-2 和審閱 #02 發現 #3 已經充分討論過。結論是 O1 = 取消補堂專用（精準、可控），O5 = 完整定義（全面但需 UI 支援）。分工合理。

**建議**：**選項 A** — 接受分工。不建議階段 A 就把 O1 泛化為「變更後該生在相關 schedule 上無資格的出席」。理由：

- 泛化掃描需要跨 table 查 enrollment + trial + all leave，效能和複雜度都比 O1 的「沿 makeup_schedule_id 查 peers」高一個量級
- 泛化掃描會撈出很多 O5 該處理但 O1 不該動的列（退讀殘留、歷史手動點名等）
- O1 的 Confirm 文案設計是圍繞「取消補堂」語境，泛化後文案會失準

**優先級**：P2 — 維持現方案。

## FP-5：範圍膨脹延遲止血

**判決**：Agree — 這是最務實的風險。方案從「攔截＋Confirm」膨脹到 O1-audit + 樂觀鎖 + peers + eligibility + O1t + O1-rollcall + O2 RPC 門檻。

**理由**：每一項加進去都有正當理由（都是審閱挖出的真實漏洞），但累積效果是把「最小可驗證成功」推遠了。

**建議**：**選項 B 的變體** — 階段 A 切兩刀，不降正確性：

**A1（必做，先上）**：
- O1-audit（會拋錯的 audit helper）
- O1 核心：攔截 deleteLeave + updateLeave（清／改調堂，含 eligibility 過濾 + peers 展開）
- 三路 Confirm + 樂觀鎖
- 執行順序：掃描 → Confirm → lock → audit → 刪 attendance → 改 leave
- O6 文件

**A2（隨後，可隔週）**：
- O1-rollcall（點名寫回防護）
- O1t（試堂 lightweight）
- O2（admin 單列刪，含過渡方案）
- ADV-P1-7（setLeaveTuitionDisposition 旁路）

A1 單獨上線就能解林藝涵主路徑（取消已點名補堂 → 一併刪 → 已上堂數對），且不產新洞（eligibility + audit + 樂觀鎖都在）。A2 是護欄和擴面。兩刀加起來與現階段 A 等價，但 A1 的範圍是可控的。

**優先級**：P0 — 開工前決定 A1/A2 切分。

## FP-6：老師路徑與行政路徑政策不一致

**判決**：Agree — 不一致存在，但**方向正確**。老師不應有權力刪計費出席。

**理由**：行政三路 Confirm vs 老師失敗，不是 bug 是權限設計。張力在於「失敗後怎麼辦」沒寫死。

**建議**：**選項 A** — 維持老師失敗，O6 必須寫清 SOP：

> 老師請假精靈清調堂遇已點名補堂 → 失敗提示列出學生姓名＋請假 ID → 老師通知行政 → 行政在請假管理處理（三路 Confirm）→ 完成後老師可繼續精靈

不可開選項 B（老師也可刪）——老師 RLS 對 attendance 沒有 DELETE，且政策上老師不該刪計費紀錄。

**優先級**：P1 — O6 補 SOP。

---

## FP-7：「一併刪」不可逆

**判決**：Agree — 硬刪不可逆是風險，但**本期接受**。

**理由**：這個取捨在原始方案和審閱 #01 都討論過。Soft-delete 的價值在 O5 上線後會更明顯（健康檢查可區分「已處理孤兒」vs「待處理孤兒」），但階段 A 不需要。

**建議**：**選項 C** — 硬刪但對計費列加二次摩擦：

- 若可刪列中含任何 `isBillableAttendanceStatus = true` 的列 → Confirm 的「一併刪」按鈕文案改為「⚠️ 刪除計費出席（影響已上堂數）」
- 可選：計費列 ≥ N 筆時要求 `confirmInput` 輸入學生姓氏（方案模擬 3 已提）

Soft-delete 留待階段 C（O5 前）重新評估。

**優先級**：P2 — 文案強化即可。

## 三題直答

### 1. 階段 A 最小成功條件（三條驗收句）

以原目標（林藝涵：取消補堂後點名紙無名、出席消失、已上堂數回退）為準：

> **V1**：取消已點名補堂之請假 → Confirm 列出可刪列 → 選「一併刪」→ `attendance_details` 對應列已刪、`leave_makeup_records` 已刪、該生已上堂數減少對應堂數。  
> **V2**：改調堂日（`makeup_schedule_id` A→B）→ Confirm 列出舊宿主 A 的可刪列 → 選「一併刪舊」→ A 出席已刪、B 無殘留、leave 已更新。  
> **V3**：選「保留出席」→ leave 已刪或已更新、attendance 仍在、該生出現在 O0／O5 健康檢查（階段 B/C）或至少 admin 可透過既有 attendance 列表看到。

### 2. 「保留出席」是否應降級或拿掉？

**不拿掉，但降級**。具體做法見 FP-1 建議（預設一併刪、保留需二次 Confirm、文案加 ⚠️ 前綴）。

理由：模擬 3（學生真有上課、行政誤取消請假）是真實場景。如果只有「一併刪」，行政會被迫在「放棄取消請假」和「刪掉真上課紀錄」之間二選一，兩者都錯。「保留出席」是正確的第三條路——只是不該和「一併刪」平起平坐。

### 3. 補完 P0 後是否仍同意可開工？

**同意可開工**，但建議先切 A1/A2（見 FP-5）。條件：

- A1 範圍內的 P0 全數寫入方案（ADV-P0-1 eligibility、ADV-P1-7 type 離調堂）
- A1 的 O1-audit + O1 核心 + 樂觀鎖 + 執行順序完整規範
- FP-1（保留出席摩擦）、FP-3（溝通範圍）、FP-6（老師 SOP）的文案級決定寫入方案或 O6
- A2 項目明確標「階段 A 第二批」，不阻擋 A1 上線

## 結論

方案沒有偏離原目標——林藝涵主路徑從頭到尾都是對的。三輪審閱加對抗模擬加進來的護欄不是 scope creep，是防回歸。但 FP-5 的風險是真的：護欄和核心綁在一起會延遲上線。A1/A2 切分是解決這個的正確手段。

這是我四輪審閱（#01–#04）的最終建議。方案現在的成熟度足以開工 A1。
