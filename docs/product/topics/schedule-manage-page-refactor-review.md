| 欄位 | 值 |

| 對象 | [`schedule-manage-page-refactor.md`](./schedule-manage-page-refactor.md) |
| 日期 | 2026-09-03 |
| 目的 | 記錄方案審閱中發現的問題，以及開工前必須由使用者確認的細節 |

## 一句

技術契約大致正確；最大風險是互動主動作與預覽模式可能偏離前線「按日期作業」習慣。下列事項拍板前，不建議開波次 3／4 的 UI 重整。

## 總判斷

方案應保留的核心：

- 基本列 → 輕量摘要 → 完整 context 分層
- KPI 與清單範圍分開；未知不顯示為 `0`
- 待處理取消「數字＝專用結果列數」
- 三種視圖是三種工作，不是三種皮膚
- 摘要必須共用點名 eligibility；做不到就縮完整 context 範圍，不用近似規則

以下問題不否定上述方向，而是要求補契約或改互動選擇。

---

## A. 撰寫／文件結構問題

### A1. 產品契約與實作清單混在同一層

現稿把使用者互動、hook 名、檔名、migration 安全、測試矩陣平鋪。審閱時容易卡在檔名，卻漏掉真正要拍板的 UX。

建議：主稿濃縮為「問題 → 互動契約 → 資料／快取／RPC 契約 → 驗收」；檔案邊界、波次細節、完整測試清單改附錄或開工後再鎖。

### A2. 決策缺少「現況 → 新契約 → 為何」一行

主點擊、待處理 scope、預覽只讀等決策，理由散落在多節。審閱者要自己拼。

### A3. 「未知≠0」重複過多

正確，但多次重述。應寫一次總則，其餘交叉引用。

### A4. `open` 階段過早鎖死檔名

§10 檔名清單像實作 checklist。審閱階段用責任邊界即可（日期裁決／清單資料／三種視圖／預覽／詳情）；檔名留給開工。

### A5. 缺少前線一日路徑

沒有短劇本，很難判斷主點擊／預覽是否合理。至少補：

1. 老師早上：看今日堂 → 展開名單 → 點名
2. 行政：點待處理取消 KPI → 處理 → 返回原日期／視圖
3. 行政桌面：日視圖調課室／代堂 → 多數情況不開詳情

### A6. 「日／週曆」範圍含糊

全文混用日視圖與日／週曆。若第一波不做週視圖，主稿應寫死「保留現有日視圖；週視圖不在本題」。

## B. UI／互動問題

### B1. 主點擊＝開紀錄（最大疑慮）

方案把卡片主區改為開啟排程紀錄，「展開名單」改獨立按鈕。

對學生／班別列表合理；對**按日期**未必：

| 角色／情境 | 高頻動作 | 開紀錄是否第一優先 |
| --- | --- | --- |
| 老師／手機按日期 | 看誰來、請假、試堂、點名 | 通常否 |
| 行政日視圖 | 調課室、代堂、取消 | 通常否 |
| 桌面列表核對 | 掃欄、開詳情 | 較可能是 |

風險：最常用的「看名單」多一步，老師／手機會覺得退步。

### B2. 排程套用右側預覽的效益未證明

學生／班別是穩定實體；單堂排程是短生命週期作業。若點列 → 預覽摘要 → 再點「點名／完整詳情」，而取消／代堂／編課室仍在列上或詳情，預覽可能變成多一層、少做事的殼。

### B3. 待處理取消專用模式的 UI 殼不足

資料契約（`scope=pending-cancelled`、數字＝列數）正確。缺的是模式可見性：

- 明顯標題／橫幅：「待處理取消（今天起）」
- 單一明確「返回原日期／視圖」
- 進入後篩選是否清空或凍結

### B4. 詳情四個分頁可能過切

概覽／名單與出席／請假與補堂／備註與操作，對單堂偏碎。前線常要「名單＋狀態＋下一步」同屏。

### B5. 概覽區資訊層級未定

「今天 KPI」與「目前範圍內未編課室／未指派」放同一概覽，有語意區分，但未定視覺層級。風險是桌面首屏又卡又雜。

### B6. 展開名單與摘要載入的按鈕狀態未寫死

摘要未完成時，展開按鈕是 disabled、可按但 skeleton，還是按下才拉完整 context？三種視圖若不統一會各做各的。

---

## C. 技術提醒（通常不必另拍板，但要寫進契約）

1. 波次 2（摘要 RPC）與波次 3（UI）耦合高：摘要未上線前，UI 可先做未知態；不可先上「假人數」篩選。
2. generation／key 雙核對、空日可快取、寫入後分層 invalidate：應維持。
3. 摘要做不到與點名 eligibility 一致時：退回縮短完整 context 範圍，不上線簡化摘要。
