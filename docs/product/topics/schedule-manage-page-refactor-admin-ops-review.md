# 排程管理頁重整方案：日常行政營運審閱

- 審閱日期：2026-09-03
- 審閱對象：[`schedule-manage-page-refactor.md`](./schedule-manage-page-refactor.md)
- 審閱角度：日常排程管理、行政操作效率、資料可信度及上線風險
- 文件性質：方案評論及開工前建議；不改動既有排程、點名、補堂、代堂或功輔佔室規則

## 結論

方案整體方向正確，尤其應優先落實：

- 基本排程列、輕量摘要及完整名單分層載入；
- 保留按日期、列表及日／週曆三種不同工作視圖；
- KPI 與目前瀏覽日期範圍分離；
- 待處理取消的數字與實際結果使用同一查詢契約；
- 未知資料不得顯示為 `0`；
- 加強日期、角色範圍、快取及請求競態控制。

不過，方案目前仍未完整處理日常行政的操作連續性。最重要的缺口是：

1. 「待處理取消」尚未有真正的結案定義；
2. 未列出完整的現有操作保留清單；
3. 卡片主點擊改動可能令查看名單的高頻工作變慢；
4. 進入完整詳情後，返回列表的位置及狀態未有保證；
5. 右側預覽的角色、畫面寬度及日視圖影響未有充分定義；
6. 寫入成功但重新載入失敗時，仍可能顯示舊值；
7. 這類互動重整不能只靠純函式測試及 build 驗證。

因此，本審閱建議「有條件通過」：資料架構可採用，但 UI 波次開工前應先補齊本文列出的營運契約及驗收情境。

## 2. 現行排程管理頁的日常行政工作

目前 `/Schedule` 不是單純的排程列表，而是一個同時承擔瀏覽、排程、課室、名單及點名入口的日常工作台。

### 2.1 日期範圍及進頁行為

現行頁面一般載入由起始日起計 14 日的排程。

初始日期優先次序為：

1. 有效 URL 日期；
2. 相同老師範圍及日期的清單快取；
3. 今天起最近一個有課日期；
4. 今天。

日視圖使用 `?view=day&date=YYYY-MM-DD` 同步日期。現行程式已有保護，避免在日期初始化前把今天寫回 URL，覆蓋最近排程日期。

### 2.2 三種工作視圖

#### 按日期

這是預設視圖，也是行政、老師及手機最直接的逐日工作方式。

每個日期分組顯示：

- 當日堂數；
- 班別、時間、老師、課室及狀態；
- 點名冊人數；
- 試堂、請假、補堂及錄影提示；
- 加堂、代堂、未有學生報讀及功輔佔室標記。

卡片主區目前用於展開名單，而不是開啟排程詳情。

#### 列表

現行桌面列表適合快速掃描多堂排程，並提供狀態、點名、代堂及刪除入口。

目前是頁內自訂表格，未使用共用 sticky table，也未有表頭排序及欄位篩選。

#### 日視圖／手機週曆

桌面日視圖以課室及時段顯示當日排程，可：

- 拖曳排程到另一課室或時段；
- 使用「移動到……」選擇目標；
- 檢查本地及遠端課室衝突；
- 一鍵分配未編課室的排程；
- 顯示非標準時間排程；
- 顯示當堂學生及請假、試堂、補堂、網課、錄影等提示。

手機的「週曆」實際上是七日日期導覽，再顯示所選一日的課室排程，並不是同時展示七日所有課堂的完整週視圖。重整文件應把這個範圍寫清楚，避免實作人員誤以為要新增完整週排程。

### 2.3 現有篩選

現行篩選使用持久狀態保存，包括：

- 狀態：全部、正常、完成、取消；
- 問題／類型：
  - 未有學生報讀；
  - 私人課程；
  - 未有課室安排；
- 老師，包括「未指派」。

老師角色只看到自己作為現任或原任老師的排程，不顯示其他老師篩選，問題篩選亦只保留與自己工作相關的項目。

「未有學生報讀」依賴完整名單資料；名單尚未完成載入時，現行按鈕會停用，避免把未知誤當為無人。

### 2.4 現有 KPI

頁首顯示：

- 今日課堂；
- 待處理；
- 上堂學生。

KPI 已經不是直接從目前 14 日清單計算：

- 今日堂數及取消堂數來自 `get_schedule_manage_stats`；
- 今日學生數另行載入今天排程的完整名單後逐堂加總；
- 查詢失敗時顯示「—」，不是 `0`。

現有主要問題是：

- KPI 的「待處理」計算今天起全部取消堂；
- 點擊卡片後，只在目前已載入的 14 日排程中套用取消篩選。

因此可能出現 KPI 顯示 8 堂，但結果只看到 2 堂。

### 2.5 現有排程操作

行政及具備 `schedule.reschedule` capability 的角色目前可在排程頁執行：

- 新增排程；
- 選擇班別、日期、開始及結束時間；
- 標記加堂及挑選加堂名單；
- 查看老師時間衝突；
- 直接更改課室；
- 更改正常／完成／取消狀態；
- 填寫取消原因；
- 處理 soft cancel 相關影響；
- 指派、更改或取消代堂；
- 開啟請假管理；
- 開啟補堂／試堂管理；
- 開啟點名紙；
- 刪除排程；
- 匯出目前篩選結果。

日視圖另支援：

- 拖曳改課室及時間；
- 「移動到……」；
- 課室衝突檢查；
- 一鍵分配課室。

### 2.6 功輔佔室

功輔佔室排程有獨立保護：

- 不應點名；
- 不應取消或刪除；
- 放假應使用功輔校曆；
- 改課室時會同步寫回當日編更；
- 加開或收起第二房應由當值編更處理。

重整不能只保留「佔室」標籤，亦必須保留以上操作限制及同步寫入。

### 2.7 名單及點名

按日期及列表目前可展開單堂名單，內容包括：

- 班內學生；
- 單堂報讀但沒有選擇此堂的學生；
- 請假學生；
- 試堂學生；
- 來此補堂學生；
- 個別學生通知按鈕；
- 班別及教學紀錄摘要；
- 前往快速檢視、完整排程頁及班別詳情的捷徑。

點名入口會先確認是否有可點名對象，並支援連堂及 `schedule_id` 深連結。

### 2.8 現有詳情

目前已經有兩種詳情：

1. 排程頁內的快速 Dialog；
2. `/Schedule/:scheduleId` 完整排程頁。

完整排程頁不是新功能，目前已包含：

- 基本排程資料；
- 班別、老師及課室捷徑；
- 學生名單；
- 單堂未選學生；
- 加堂名單挑選；
- 請假紀錄；
- 來此補堂；
- 錄影提示；
- 網課提示；
- 已存檔出席；
- 教學紀錄；
- 排程備註；
- 狀態、加堂、代堂及刪除操作。

方案中的完整紀錄頁工作，實際上主要是重新整理資訊架構、分頁、載入方式及流動裝置外殼，而不是從零新增詳情能力。

## 3. 現行資料載入及技術限制

### 3.1 一般載入流程

現行 reload 大致依序執行：

1. 並行取得 14 日排程基本列及全部課室；
2. 先顯示基本列，此時點名冊人數為未知；
3. 另行載入今日 KPI；
4. 對 14 日內全部排程取得完整 `get_teacher_schedule_roster_context`；
5. 在前端補回每堂點名冊人數、試堂、請假、補堂及點名資格；
6. 把基本列、完整 roster context、提示及課室一起寫入清單快取；
7. 展開名單或進入日視圖時，仍可能作額外資料處理或查詢。

這個流程的正確性較高，但一般瀏覽亦要下載完整學生資料，成本過重。

### 3.2 現有快取限制

現有排程快取已包含：

- 老師範圍；
- 起始日；
- 結束日；
- 排程列；
- 課室；
- 完整 roster context；
- 排程提示。

但空結果被視為不可使用，因此真正沒有排程的日期返回後仍會再次查詢。

另外，快取要等待整段完整名單完成後才有完整資料，未有正式的基本列／摘要完成狀態。

### 3.3 單一大型元件

`ScheduleManagePage.tsx` 同時承擔：

- 日期及 URL；
- 快取；
- KPI；
- 全區間資料載入；
- 篩選；
- 三種視圖；
- 展開名單；
- 快速詳情；
- 新增、移動、取消、代堂、刪除、點名及一鍵分配；
- 多個 Dialog 的狀態。

問題不只是檔案長度，而是日期、載入、寫入及畫面互相依賴。一項改動容易影響其他流程。

### 3.4 請求競態

現行主 reload 已使用 generation 防止舊日期結果覆蓋新日期，但展開名單、日視圖名單及其他按需載入多數只使用 effect cleanup 的 `cancelled` boolean。

快速切換日期、老師或排程時，仍需要更完整的查詢 key 及世代核對。

## 4. 方案前後的主要分別

### 4.1 資料載入

現況：

- 14 日基本列後，載入整個範圍的完整學生 context；
- 清單、提示及人數等待同一份重資料；
- 快取連同完整 roster context 儲存。

方案：

- 首屏只載入基本排程列；
- 另以批量 RPC 載入輕量摘要；
- 完整學生資料只在所選日期、展開名單、預覽、詳情或點名時載入；
- 基本列及摘要都有獨立狀態；
- 只有摘要完成後，清單快取才標為 fresh。

### 4.2 待處理取消

現況：

- KPI 查今天起全部取消堂；
- 點擊只篩目前 14 日列。

方案：

- 使用 `scope=pending-cancelled` 專用查詢；
- KPI 數字與結果使用同一份資料或同一 SQL 謂詞；
- 返回後恢復原日期及視圖。

### 4.3 卡片互動

現況：

- 按日期卡片及列表列主點擊用於展開名單；
- 日視圖卡片開快速 Dialog；
- 完整詳情另有按鈕或路由。

方案：

- 主點擊改為開啟排程紀錄；
- 展開名單改為獨立按鈕；
- 桌面行政／外星人使用右側預覽；
- 管理層、財務、老師及流動裝置進入完整詳情。

### 4.4 完整詳情

現況：

- 單頁長卷；
- 進頁時載入完整 roster context 及詳情 context；
- 排程備註只有「有未儲存變更」提示，未完整保護離開。

方案：

- 桌面為一般完整頁面；
- 手機使用 adaptive bottom sheet 外觀；
- 分為概覽、名單與出席、請假與補堂、備註與操作；
- 分頁與 URL 同步；
- 完整 context 按需要載入；
- 加入未儲存離開保護。

### 4.5 列表

現況：

- 自訂固定欄位表格；
- 無共用 sticky table；
- 無表頭排序及欄位篩選。

方案：

- 改用共用 sticky table 規範；
- 加入排序及表頭篩選；
- 保留一般狀態、問題及老師篩選。

## 5. 對日常行政的正面影響

### 5.1 開頁及換日期更快

行政可以先看到日期、班別、時間、老師、課室及狀態，不必等待 14 日完整學生資料。

這對以下工作尤其有利：

- 早上快速查看當日課堂；
- 臨時查下一堂課室；
- 切換老師範圍；
- 查看未編課室或未指派老師；
- 由詳情返回列表。

### 5.2 減少把未知資料當成真實零值

名單摘要尚未完成時顯示 skeleton 或「—」，可避免：

- 誤以為班別沒有學生報讀；
- 誤以為無須點名；
- 把統計載入失敗解讀為沒有課堂；
- 因錯誤人數而錯誤安排課室或老師。

### 5.3 三種視圖保留正確工作分工

方案沒有把所有排程工作強制放入同一表格：

- 按日期繼續支援逐日處理；
- 列表支援大量核對及匯出；
- 日視圖保留課室與時段的空間關係、拖曳及衝突檢查。

這符合排程工作的實際需要。

### 5.4 待處理取消的數字與結果一致

獨立查詢範圍可以消除「數字有 8、清單只有 2」的落差，亦不會因使用者正在查看其他日期而改變 KPI。

### 5.5 詳情較容易定位資料

現有完整頁面內容很多。合理分區後，行政可更快找到：

- 名單及出席；
- 請假及補堂；
- 教學紀錄及排程備註；
- 狀態及代堂操作。

### 5.6 返回列表可以更快

只要快取鍵及失效正確，從詳情返回相同日期範圍時，可以先顯示原有列表，再背景更新。

### 5.7 減少不必要的學生資料下載

一般瀏覽只需摘要，不需先下載所有學生姓名、聯絡資料、報讀、試堂、請假、補堂及出席明細，有利效能及資料最小化。

## 6. 問題、負面影響及改善建議

### 6.1 「待處理取消」目前不是真正的待辦佇列

現有 `get_schedule_manage_stats` 實際計算：

- 日期由今天起；
- 狀態包含取消；
- 取消原因不是校舍假期。

它沒有判斷該取消堂是否已經：

- 安排改期；
- 安排補堂；
- 完成通知；
- 決定毋須補堂；
- 退款或以其他方式結案。

因此，「真正待處理」這個名稱超出了現有資料契約。已處理的未來取消堂仍可能一直留在數字內。

#### 建議

本次應先二選一：

1. 若不新增結案機制，把 KPI 及模式改名為「未來取消堂」；
2. 若確實要成為待辦佇列，另行定義：
   - 處理狀態；
   - 處理方式；
   - 負責人；
   - 完成時間；
   - 如何重新開啟；
   - 哪些取消毋須補堂。

不應只靠是否存在 `makeup_of=` 判斷是否完成，因為並非每一項取消都以補堂結案。

### 6.2 待處理模式與原有篩選可能互相抵消

目前篩選條件以 AND 疊加。若使用者原先選了「正常」，進入取消範圍後仍套用該條件，畫面可能變成空白。

老師、問題及狀態篩選亦會令 KPI 總數與畫面列數再次不一致。

#### 建議

待處理模式應有獨立的篩選契約：

- 進入時暫停套用一般狀態及問題篩選；
- 原有篩選保留在記憶體，退出後恢復；
- 模式內只提供與取消跟進有關的篩選；
- 如仍允許老師篩選，清楚顯示「全部數量」及「目前篩選數量」；
- 顯示固定橫幅「未來取消堂／待處理取消（今天起）」；
- 提供單一清楚的「返回原日期及視圖」按鈕。

待處理結果跨越任意日期，不應保留日視圖。建議固定使用按日期或列表，並按最早日期排序。

### 6.3 未明確保證所有現有高頻操作

方案表示三種視圖功能不減少，但明確列出的就近操作主要是課室、狀態、點名及代堂。

以下現有能力未被逐項寫入驗收：

- `+請假`；
- `+補堂試堂`；
- 個別學生通知；
- 加堂名單挑選；
- 標記加堂；
- 新增排程；
- 刪除排程；
- CSV 匯出及匯出欄位；
- 教學紀錄摘要；
- 班別及老師捷徑；
- 取消原因；
- 連堂點名；
- 功輔佔室限制及同步編更。

#### 建議

在主方案加入「現有操作保留矩陣」，按以下維度逐項驗收：

- 視圖：按日期／列表／日視圖；
- 裝置：桌面／手機；
- 角色：行政／管理層／財務／老師／外星人；
- 操作：查看／寫入／點名／捷徑／匯出。

沒有列入矩陣的現有操作，不應在重整過程中默認刪除。

### 6.4 卡片主點擊改動會影響既有操作習慣

現時按日期卡片的主點擊是展開名單。方案改為開啟預覽或完整記錄。

這對桌面列表可能合理，但對以下情境可能是退步：

- 老師查看今天有哪些學生；
- 行政快速確認請假、試堂及補堂；
- 手機查看下一堂名單；
- 點名之前先核對學生。

如果「展開名單」改成較小的次要按鈕，高頻工作會多一步，而且更容易誤入完整詳情。

#### 建議

主動作應按視圖決定，而不是全頁統一：

- 按日期，尤其手機及老師：主區可繼續展開名單；
- 列表：主列可開預覽或詳情；
- 日視圖：主動作維持課室／時段工作，詳情屬次要入口。

若仍採用現稿：

- 「展開名單」必須是清楚、足夠大的可見按鈕；
- 不應只使用細小 chevron；
- 首次推出時提供簡短提示；
- 展開名單後仍可容易開啟排程詳情；
- 選取預覽不應自動收起已展開名單。

### 6.5 手機 bottom sheet 不會自然保留原列表

`/Schedule/:scheduleId` 是獨立路由。進入後，原本的排程列表 React 樹會卸載。

即使手機使用 bottom sheet 外觀，背景也不是仍然存在的排程列表。清單快取只能減少重新下載，不能自動恢復：

- 原有捲動位置；
- 展開的排程；
- 選取列；
- 待處理模式入口位置；
- 日視圖的水平捲動位置。

#### 建議

詳情入口應保存返回狀態：

- 原路由及 query；
- 視圖；
- 日期；
- 篩選；
- 所選排程；
- 捲動 anchor 或排程 ID。

返回後先恢復清單，再把該排程捲回可見範圍。不能只依賴 `navigate(-1)` 及資料快取。

### 6.6 右側預覽的角色範圍不完全符合操作能力

方案只讓桌面行政／外星人使用右側預覽，管理層則直接進完整詳情。

但管理層同樣可具備 `schedule.reschedule`，會處理排程。相同工作因角色不同而失去保留列表上下文的能力，操作效率不一致。

#### 建議

- 重新評估管理層是否也應使用排程預覽；
- 若維持排除，文件應記錄營運原因，而不只是沿用既有決定；
- 財務及老師可以繼續直接進唯讀或獲授權的完整詳情。

### 6.7 右側預覽可能令列表及日視圖過窄

現有 Record Preview Rail 最寬約 26rem，亦可佔 42vw。只以「不是手機」判斷時，小型手提電腦或平板橫向畫面可能同時容納：

- 側欄；
- 主排程頁；
- 右側預覽。

日視圖及最小寬度列表會被明顯壓縮，增加水平捲動。

#### 建議

- 只在較寬桌面，例如 `xl` breakpoint 以上啟用；
- 中等寬度改為覆蓋式預覽或直接開完整詳情；
- 日視圖可延後啟用右側預覽，第一波先限列表；
- 開始拖曳或移動排程時，自動關閉或凍結預覽，避免格線尺寸突然改變。

### 6.8 預覽若完全只讀，可能成為多一層操作

方案把預覽定位為快速判斷，不放入取消、名單編輯或刪除流程，這可避免兩套表單分叉。

但若預覽只有摘要及「前往完整詳情」，行政可能要：

1. 點排程；
2. 看預覽；
3. 再點完整詳情；
4. 才能執行操作。

這比現有快速 Dialog 或就近操作多一層。

#### 建議

預覽可以保持沒有重複表單，但提供共用操作觸發器：

- 點名；
- 指派／更改代堂；
- 取消；
- 開啟班別；
- 開啟老師；
- 開啟完整詳情。

取消及代堂仍使用現有共用 Dialog，不需要在預覽內另建表單。

第一波亦可只在列表視圖啟用預覽，以實際使用情況驗證其價值。

### 6.9 四個詳情分頁可能過度切割

單堂排程通常是短時間處理工作。行政可能需要同時看到：

- 基本資料；
- 學生名單；
- 請假／補堂提示；
- 狀態及下一步。

分成四個 tab 後，常見核對可能需要反覆切換。

#### 建議

可先評估兩個 tab：

1. 概覽與操作；
2. 名單與出席，並把請假、補堂、錄影及網課提示放在同一工作脈絡。

如維持四個 tab：

- 頁首必須持續顯示班別、日期、時間、老師、課室及狀態；
- 重要異常應跨 tab 顯示摘要；
- tab 標籤可顯示數量，例如「請假與補堂 3」；
- 點擊預覽中的請假提示應直達對應 tab。

### 6.10 寫入成功後不應繼續顯示舊值

方案提出寫入後 invalidate 並重抓；重抓失敗時保留舊列並標示 stale。

對一般清單這個策略可接受，但以下操作若成功寫入後仍顯示舊值，容易令行政重複操作：

- 取消排程；
- 改課室；
- 移動時間；
- 指派代堂；
- 標記加堂；
- 刪除排程。

#### 建議

寫入服務成功後：

1. 以服務回傳結果立即局部更新或移除該列；
2. 把相關快取標為 stale；
3. 背景重新核對；
4. 核對失敗時顯示「已儲存，但未能重新核對最新列表」；
5. 不應把已知成功的變更重新顯示為舊狀態。

如無法局部更新，至少把該列鎖定並標示「變更已儲存，正在更新」。

### 6.11 完整 context 跨頁快取第一波風險較高

完整名單會受以下工作改變：

- 點名；
- 請假；
- 試堂；
- 補堂；
- 加堂名單；
- 單堂選擇；
- 名單政策；
- 宣告。

這些寫入分散在多個頁面及服務。任何一個入口遺漏失效，都可能在詳情或展開名單中顯示舊資料。

#### 建議

第一波只做：

- 同一排程詳情生命週期內載入一次；
- 同一展開區域內避免重複請求；
- 關閉或離開後不保留跨頁完整 context。

待所有寫入入口都有集中 invalidation 或版本機制後，再加入跨頁短期 context 快取。

### 6.12 「上堂學生」KPI 名稱不夠準確

現行算法把今天每堂點名冊人數加總。同一學生若同日上兩堂，會計兩次。

因此這個數字實際上是「學生人次」，不是不重複學生數。

#### 建議

- 若保留逐堂加總，改名為「今日學生人次」；
- 若行政需要知道今天實際到校人數，改為 distinct student count；
- 如兩者都有價值，可分別顯示，但不要以同一名稱混用。

### 6.13 匯出時要處理摘要尚未完成

目前匯出可在點名冊人數仍未完成時執行，未知人數會成為空白欄。

分段載入後，這個情況更常見。

#### 建議

- 摘要尚未完成時停用包含人數的匯出；
- 或顯示確認訊息，明確說明部分摘要尚未完成；
- 匯出檔應標明日期範圍、套用篩選及產出時間；
- 待處理模式匯出應使用專用查詢的全部結果，不可只匯出目前畫面已完成分段載入的列。

### 6.14 跨午夜更新要連同 KPI 及 scope 更新

方案提出跨午夜或重新取得焦點時更新「今天」。

只更新前端日期文字不足夠，還需要：

- 重新查詢今日堂數；
- 重新查詢今日學生人次；
- 以新的 `asOf` 重建取消 scope key；
- 更新今天標記；
- 視需要更新校舍假期提示。

建議把這些行為寫入驗收，而不是只測 `todayYmd` 改變。

### 6.15 摘要 RPC 是正確性最高風險

摘要不能用「班別目前就讀中人數」近似點名冊，否則會誤算：

- 暑期第一期／第二期；
- 單堂指定排程；
- 試堂；
- 來此補堂；
- 加堂挑選名單；
- 宣告繼承；
- `makeup_of=` 對 26SM 暑期期數的影響；
- 退讀生效日期。

#### 建議

維持原方案的硬性要求：

- 摘要與完整點名 context 共用 eligibility；
- 以資料庫案例測試逐一對照兩者；
- 無法證明一致時，退回縮短完整 context 的排程 ID 範圍；
- 不以錯誤摘要換取速度。

### 6.16 純函式測試不足以驗證這類 UI 重整

方案的資料及狀態測試方向正確，但以下風險不能由純函式測試、lint 或 build 發現：

- 卡片主點擊與展開按鈕互相冒泡；
- 右側預覽令列表或日視圖過窄；
- sticky table 的表頭及橫向捲動；
- 手機 bottom sheet 關閉及返回；
- 拖曳後確認 Dialog；
- 快速連續切換排程；
- 未儲存備註離開保護；
- 詳情返回後的捲動位置；
- 不同角色的操作控件是否正確隱藏。

#### 建議

即使不使用 Browser MCP，上線前仍需由行政按本文第 8 節進行手動驗收，並記錄結果。

## 7. 建議修改優先次序

### 開工前必須定案

1. 「待處理取消」究竟是未來取消堂列表，還是真正可結案的工作佇列；
2. 待處理模式如何處理原有篩選及返回狀態；
3. 按日期、列表及日視圖各自的主點擊行為；
4. 完整現有操作保留矩陣；
5. 詳情返回時的日期、視圖、篩選及捲動恢復；
6. KPI「上堂學生」是學生人次還是不重複學生；
7. 手動營運驗收清單。

### 第一波實作應完成

1. 日期 controller 及 canonical key；
2. 基本列與摘要分層；
3. 摘要與完整 roster 一致性測試；
4. 待處理取消專用結果；
5. 空結果快取；
6. 寫入後局部更新及精確失效；
7. 按日期、列表及日視圖功能不減少；
8. 角色 capability 回歸；
9. 返回狀態恢復。

### 可延後

1. 完整 context 跨頁快取；
2. 排程右側預覽擴展至所有視圖；
3. 管理層是否加入右側預覽；
4. 四 tab 詳情進一步細分；
5. 額外通用狀態框架。

## 8. 建議手動營運驗收情境

### 情境一：行政早上查看今天安排

1. 進入排程管理；
2. 今日課堂及學生人次顯示正確；
3. 首屏先顯示基本排程；
4. 摘要載入前不顯示錯誤 0；
5. 切換到今天日視圖；
6. 查看未編課室及未指派老師；
7. 展開一堂名單；
8. 開啟點名；
9. 返回後仍在原日期及位置。

### 情境二：處理取消堂

1. 從其他日期範圍點擊取消 KPI；
2. 進入明確的取消專用模式；
3. 結果數量與 KPI 一致；
4. 原有「正常」篩選不會令結果消失；
5. 取消結果按日期排序；
6. 開啟其中一堂，查看取消原因及相關提示；
7. 返回專用結果；
8. 再返回原日期、視圖、篩選及位置。

### 情境三：行政調整課室

1. 在日視圖選擇日期；
2. 拖曳一般排程；
3. 系統檢查課室衝突；
4. 確認後畫面立即顯示新課室及時間；
5. 模擬重新核對失敗時，不回復顯示舊值；
6. 使用「移動到……」重做一次；
7. 對功輔佔室只改課室，不改時間；
8. 確認當日編更同步。

### 情境四：一鍵分配課室

1. 建立多堂未編課室排程；
2. 執行一鍵分配；
3. 已佔用課室不被重複分配；
4. 取消堂及功輔佔室按既定規則處理；
5. 顯示成功及未能分配數量；
6. 列表及日視圖同步更新。

### 情境五：代堂

1. 指派單堂代堂；
2. 指派連堂代堂；
3. 原任及實際授課老師顯示正確；
4. 老師衝突只提示，不錯誤改班別任教老師；
5. 已點名後依既定規則限制取消代堂；
6. 返回列表後代堂標記即時更新。

### 情境六：取消排程

1. 把正常排程改為取消；
2. 必須輸入取消原因；
3. soft cancel 相關確認正常；
4. 校舍假期不會被建立為取消堂；
5. 功輔佔室沒有取消入口；
6. 寫入成功後列表立即顯示取消；
7. 取消專用模式同步更新。

### 情境七：名單及點名

1. 一般報讀學生正確；
2. 暑期第一期／第二期正確；
3. 單堂指定及未選正確；
4. 試堂正確；
5. 來此補堂正確；
6. 加堂挑選名單正確；
7. 請假及錄影／網課提示正確；
8. 摘要人數與完整點名紙一致；
9. 連堂點名正常。

### 情境八：不同角色

#### 行政

- 可新增、移動、取消、代堂及點名；
- 如啟用右側預覽，列表仍可正常使用。

#### 管理層

- capability 與實際控件一致；
- 詳情或預覽行為有明確決定。

#### 財務

- 可查看排程、摘要及詳情；
- 不顯示可寫入課室、狀態、代堂或刪除控件。

#### 老師

- 只看到現任或原任排程；
- 沒有其他老師篩選；
- 可查看名單及依 capability 點名；
- 不因主點擊改動而增加不必要步驟。

### 情境九：手機

1. 按日期查看及展開名單；
2. 週日期導覽正常；
3. 開啟詳情 bottom sheet；
4. 關閉後恢復原日期及位置；
5. 未儲存備註時關閉會提示；
6. 列表模式不在手機錯誤顯示；
7. 操作按鈕不過小或被遮擋。

### 情境十：失敗及競態

1. 快速切換日期；
2. 快速切換老師；
3. 快速展開兩堂名單；
4. 快速切換詳情 tab；
5. KPI 成功但清單失敗；
6. 清單成功但摘要失敗；
7. 寫入成功但重抓失敗；
8. 空白日期返回後不重複查詢；
9. 頁面跨午夜後 KPI 及取消 scope 更新。

## 9. 建議補入主方案的驗收條件

除原方案驗收外，建議加入：

- 待處理取消的名稱與資料庫結案定義一致；
- 待處理模式不會被原有「正常」或其他不相容篩選清空；
- 進入及離開待處理模式時，日期、視圖、篩選及位置可恢復；
- 按日期的展開名單仍是清晰且高效的操作；
- 現有請假、補堂／試堂、學生通知、加堂名單、點名、代堂、刪除及匯出入口沒有遺失；
- 功輔佔室的寫入限制及同步編更沒有退步；
- 管理層的詳情／預覽行為已明確定案；
- 右側預覽只在有足夠寬度時啟用；
- 詳情返回後所選排程仍在可見範圍；
- 寫入成功後不重新顯示已知過時的列值；
- 摘要尚未完成時，匯出不會把未知人數當作正式空白資料；
- 「上堂學生」的名稱與計算方式一致；
- 手機 bottom sheet 的關閉、返回及未儲存保護正常；
- 跨午夜後 KPI、今天標記及待處理 scope 一併更新；
- 行政已完成手動桌面及手機驗收。

## 10. 最終判斷

這個方案最有價值的部分不是把 3,000 多行元件拆成多個檔案，而是把排程管理的資料成本及工作語意分開：

- 看排程不應先下載全部學生資料；
- 摘要不應取代完整點名資格；
- 今天 KPI 不應受目前瀏覽範圍影響；
- 課室編排不應被一般表格模式限制；
- 未載入及失敗不應被顯示為零；
- 寫入後的畫面必須反映已知成功結果。

從日常行政角度，方案值得推進，但不應原樣直接進入完整 UI 重整。建議先在主方案補定：

1. 取消堂是否有真正待辦生命周期；
2. 三種視圖各自的主動作；
3. 現有操作保留矩陣；
4. 詳情返回及捲動恢復；
5. 預覽角色及畫面寬度；
6. 寫入後局部更新；
7. KPI 名稱；
8. 手動營運驗收。

完成以上補充後，資料分層及技術架構可以進入實作。
