## 一、本身要解決的問題

### 1.1 觸發個案

Jackson Lau 班 `26SM-ENGS5009-A`：原定 7/15、7/16 因老師請假取消，改於 8/2 連堂補回。黃渲棋只報讀**第一期**，補回日落在**第二期**日曆區間，點名紙沒有其姓名；兩期全報學生則正常。即時以調堂綁定補正，並已發行政收信匣通知。

### 1.2 根因（非單一程式錯誤）

收費與點名長期使用兩套互不對齊的邏輯：

| 面向 | 現行行為 | 問題 |
| --- | --- | --- |
| 收費 | 偏「堂次數量」直覺（收四堂、一期價、按月約四堂） | 與點名資格無穩定對應 |
| 點名單堂生 | 綁定 `student_enrollment_sessions.schedule_id`，安排補堂時會改掛 | 較能跟住，但只覆蓋單堂 |
| 點名期數生（第一期／第二期／兩期全報） | 以排程**日期**對 `academic_year_periods` 推期數 | 跨期補回易被濾走；兩期全報機制與單期相同，並無特別防護 |
| 正規全期 | 「就讀中」隱含跟班內排程；單堂仍靠改掛 | 看似較少爆裂，實為缺少期數這層錯誤代理，模型仍不一致 |

一句根因：**沒有統一的「學生還有幾堂」權益帳；點名紙又常用日曆推斷資格。**

### 1.3 必須解決的具體問題

1. **跨期／改期後點名缺人**：補堂或改期後，應到學生從點名紙消失（P0）。
2. **前線心態與系統不一致**：前線認為「收了幾堂就應來幾堂；改期不改有沒有份」；系統卻用日期或半套掛堂決定名單。
3. **兩套跟堂模型**：行政以為「安排補堂＝全員跟」；實際只有單堂會改掛。
4. **手動加名繞過帳務**：點名紙跟不上時人手加名，往往只改紙、不入權益帳。
5. **多入口規則不一致**：班別詳情、欠堂對帳、WhatsApp 提醒等是否同一資格規則，尚未盤點齊。
6. **約束情境須能正確處理**（定案時須逐一答到）：
   - 交四堂、中間請假一星期 → 不可自動掛名到「之後連續四堂」
   - 提早繳費、數月後才上課 → 本月點名紙不應出現
   - 交中文後改上數學（金額相同） → 須有科目／班別命名空間，不可萬能總池
   - 請假後不調堂、順延下一期 → 與調堂補回是不同指令
   - 同時持有多個權益池（例如第一期剩餘＋另購單堂）→ 消耗優先序須寫死（見 §3.5）
7. **學年邊界**：暑期權益不得進入九月新正規班點名紙；正規補堂即使落在暑假日曆，仍消耗正規權益。
8. **不在本階段解決、但不可誤傷**：每月收款收入／消課收入認列口徑（會計另議）；不得藉點名修復改寫已繳學費。

### 1.4 前線心態（設計約束）

> 收了幾堂錢，就應該來幾堂；改期不改「有沒有份」。

系統應貼近此直覺，而非要求前線學習內部推導規則。手動加名若保留，必須走正式補宣告路徑（見 §3.8），禁止捷徑只改點名紙。

## 二、曾思考的方案與回絕原因

| 方案 | 做法摘要 | 回絕或降級原因 |
| --- | --- | --- |
| **純方案 A：只靠顯式掛堂** | 報名時為每堂鑄造掛勾；改期＝換飛 | 能回答「哪一天來」，但與前線「收 N 堂＝來 N 堂」的數量直覺相反；改期／順延／轉科時重掛負擔高；亦不自動產生「還剩幾堂」的 source of truth |
| **純方案 B：只有權益池／錢包** | 只記剩餘堂數，點名依餘額灑落所有點名紙 | 無法回答「今天誰應到」；提早繳費者會誤入本月點名紙；中間請假亦難正確處理 |
| **繼續雙模型＋補丁（現況延伸）** | 單堂改掛＋`makeup_of` 日期繼承止血 | 只能過渡；洞會再現；無 sunset 會沉澱成永久技術債 |
| **大一統只剩 N 堂、不分包裝** | 取消第一期／第二期／科目等邊界 | 破壞暑期銷售包裝與科目邊界；通常不可取 |
| **以日曆期數／學年 label 當點名主鍵** | 今日屬第幾期／幾月即決定名單 | 補堂窗與改期一旦存在即永久不成立；正是現況裂縫來源，明確淘汰 |
| **把「B＋宣告」理解成「選 B、宣告可選」** | 只建池、宣告當附加 | 兩層缺一不可；已改正表述 |
| **本階段一併重做收入認列** | 同時改錢包與每月／消課收入報表 | 會計口徑未定；**明確押後** |
| **第一期強制收款明細綁全域 `right_id`** | 收款／權益／宣告／消課一律同鍵貫穿 | 稽核關聯有需要，但會觸及收款寫入口徑；第一期改為宣告／消耗綁 `pool_id`，收款仍經既有 enrollment／payment 間接對帳（見 §3.1） |
| **「可設定」多池優先序作逃脫** | 不選規則、改成設定項 | 小機構需要一條寫死預設；設定化等於永遠不定。已選定 §3.5 |
| **期數相容矩陣／宣告時自動向下相容** | 一期餘額可自動用在二期正課 slot | 把「跨日曆補回」誤當成「須轉池」；相容＝鬆綁包裝，一期生會誤入二期正課。補回應**繼承原池宣告**，不必轉移（見 §3.2） |
| **單一佔用池（以佔用數當餘額；schedule 打期數標籤）** | 廢多狀態、用 occupancy 計「還剩幾堂」 | 權益與宣告再度混一；同堂可同時服務多包裝學生，期數不可打在 schedule 上 |

說明：早期「選 A 或選 B」問題問錯——要決定的是是否承認多本獨立帳本，以及宣告層與權益層是否同時存在。A／B 僅保留為兩層實作形狀的稱呼。

## 三、目前的方案及細節

### 3.1 定調（2026-08-04 產品已確認採納；會計仍另案）

**承認四本帳，各自獨立、各有生命週期與政策；分階段落地。**

| 帳本 | 回答的問題 | 現行狀態 | 階段 |
| --- | --- | --- | --- |
| 收款帳 | 何時收了多少錢 | 已有（`payments` 等） | 保留，本階段不改寫入口徑 |
| 權益帳 | 還剩幾堂；屬於哪一科／班／期包裝 | 基本上沒有統一池 | **第一期必做** |
| 到課宣告帳 | 本次排程點名紙應有誰 | 半套（僅單堂較完整） | **第一期必做** |
| 收入確認／消課帳 | 何時把預收轉為已消課收入 | 有點名消耗等碎片；認列口徑未定 | **第二期（會計定案後）** |

營運語意上其實是**三層**（前兩層為第一期新建；第三層沿用既有點名）：

| 層 | 職責 |
| --- | --- |
| 權益池 | 還有幾堂、屬哪個命名空間 |
| 到課宣告 | 哪次 `schedule` 應出現誰；必須指向某 `pool_id` |
| 點名結果／權益消耗 | 實際點名狀態；依政策是否扣池餘額（≠ 收入認列） |

核心原則：

1. 點名紙只回答：「這次交付是否已宣告、且該生仍擁有對應權益？」  
   不回答：「今天日曆屬第幾期／幾月／哪個 academic_year_label」。
2. **權益池與到課宣告兩層皆必須**；點名結果層已存在（`attendance_details`），須與其扣堂政策對齊，但**不**把「已認列收入」寫進宣告。
3. 到課宣告層的實作形狀＝顯式掛堂（預排自動掛、補堂改掛或繼承）；可否掛上，由權益池＋命名空間把關。
4. 淘汰「日期 → 期數／label → 點名紙」作為主路徑。
5. 會計／收入認列另花時間定案；未定前不作為實作前提，不改收入認列路徑。
6. **權益消耗 ≠ 收入認列**。欄位與事件命名用營運語意（如 `entitlement_consumed`、`lesson_right_used`），禁用 `revenue_recognized`／`earned_lesson`／`recognized_at` 等會計語義。資料註明：operational entitlement consumption, not accounting revenue recognition。
7. 第一期稽核鏈：宣告與消耗記錄綁 `pool_id`（及來源 enrollment／事件 id）；**不**要求本階段改寫 `payment_details` 強制綁新 right id。

### 3.2 權益池命名空間（唯一鍵，2026-08-04 已確認）

權益池由下列欄位唯一決定（對齊現有報讀／學年模型；實作欄名可微調，語意不可鬆）：

| 欄位 | 說明 |
| --- | --- |
| `student_id` | 學生 |
| `class_id` | 班別（科目隨班；轉科＝出舊池入新池） |
| `academic_year_id` | 學年空間（暑期包裝 vs 正規學年） |
| `package_type` | 對齊現行包裝：`summer_phase_1`／`summer_phase_2`／`summer_full`／`regular_full`／`single_lesson`（與 `enrollment_period` 對照，不是日曆推導） |
| `source_enrollment_id` | 來源報讀列（同生同班若因補購／順延產生多池時可區分） |

約束（系統強制，非僅流程約束）：

1. 宣告建立時，目標 `schedule` 所屬班別／學年空間必須與池的命名空間相符；不符則拒絕並回 reason code（見 §3.10）。
2. **不是**單靠 `schedule.date ≤ valid_until`：正規補堂可落在七至八月日曆，仍消耗正規池；暑期權益不得進入九月新正規班點名紙——以 **academic_year／package 命名空間** 匹配，而非「日期落在暑假＝暑期權益」。
3. **禁止**在 `schedule` 上打 `package_type`／期數標籤決定資格：同一堂可同時有第一期補回生與第二期／兩期正課生；包裝只掛在 **宣告→池**。
4. 單堂＝最細粒度包裝，不是第二套系統。
5. 點名資格不得由 schedule date 推 period；只能由 **declaration → entitlement_pool**。

**補回 ≠ 轉池；順延才轉池：**

| 指令 | 權益池 | 宣告 |
| --- | --- | --- |
| 跨日曆補回（觸發個案型） | **留在原包裝池**（如仍屬 `summer_phase_1`） | 新 `schedule` 建宣告，指向原池 |
| 順延下一期 | 出舊池、入新包裝池 | 本期不再自動宣告；可**期末批次**結轉，禁止靠逐堂人手「轉移」硬撐 |

可選輔助欄（非唯一鍵核心）：`valid_from`／`valid_to` 用於多池排序與過期提示；不得單獨取代命名空間匹配。

### 3.3 兩層（加結果層）如何分工

| 層 | 近似舊稱 | 職責 | 若缺少 |
| --- | --- | --- | --- |
| 權益池 | 方案 B | 有命名空間的剩餘堂次 | 無法對數、退費、防超上 |
| 到課宣告 | 方案 A 形 | 某次 `schedule` 上誰應出現在點名紙；補堂／改期改宣告 | 不知哪一天來；只能靠日期猜 |
| 點名結果／消耗 | 既有 `attendance_details`＋扣堂政策 | 實際狀態；是否減池餘額 | 池餘額與前線直覺脫節 |

前線看到「點名紙有名」＝宣告層；「有沒有權出名」＝權益池；「點了什麼、扣不扣」＝結果層＋§3.6。

### 3.4 宣告生命週期（輕量）

宣告需可取消／取代，但不把「已消耗」塞進宣告本體（消耗屬結果層）。

| 狀態 | 含義 |
| --- | --- |
| `active` | 點名紙應顯示 |
| `void` | 已作廢（取消堂、調走、轉科、順延等） |
| `superseded` | 被另一則宣告取代（可記 `superseded_by`） |

規則（暫定）：

- 已寫入計費點名結果的宣告：不可靜默 void；須走既有反操作／Confirm 路徑（見 [`ATTENDANCE_BILLING.md`](../ATTENDANCE_BILLING.md) 取消補堂／清調堂）。
- 未點名：可 void，並視事件建立新 `active` 宣告。
- **禁止**用宣告狀態表達收入認列。

### 3.5 多權益池消耗優先序（暫定寫死）

學生可能同時持有多個池（例如第一期剩餘＋另購單堂＋順延）。適用於**同班＋同學年**、且宣告**未**指定 `pool_id` 時。**選定規則（2026-08-04 已確認；實作若改句須回寫）：**

1. 宣告已指定 `pool_id` → 扣該池。
2. 否則，細粒度／特殊包裝優先於大包裝：`single_lesson`（及同類加購／贈送單堂）→ 單期（`summer_phase_1`／`summer_phase_2`）→ 全期（`summer_full`／`regular_full`）。避免短效單堂過期浪費、誤扣長效期數池。
3. 同權重內取 `valid_to` 最早且仍有餘額者。
4. 若仍並列 → 取 `created_at` 最早（FIFO）。
5. 跨科／跨班／跨學年 → **不自動扣**；必須人工（或批次）轉移後再宣告。一期↔二期**正課**不相容自動扣；補回用繼承原池宣告，不走本條「轉移」。

> 宣告指定 → 包裝粒度 → 到期日 → FIFO；跨班／跨學年禁止自動消耗。

### 3.6 何時扣權益（對照既有扣堂；≠ 收入認列）

本階段只定義**營運權益餘額**何時減少或返還，不定義會計認列。對齊 [`ATTENDANCE_BILLING.md`](../ATTENDANCE_BILLING.md)／`isBillableAttendanceStatus`：

| 點名結果（既有狀態） | 扣權益？ |
| --- | --- |
| 現場／錄影回放／zoom實時網課 | 是 |
| no show | 是 |
| 請假而不需補回 | 是 |
| 事假／病假 | 否 |
| 未點名 | 否（不自動銷堂） |
| 老師取消／排程取消（無交付） | 否；相關宣告 void；權益留在池 |
| 調堂後於補回堂之上列計費狀態 | 依上表；原請假日不因「有補回」雙扣 |
| 歷史「缺席」 | 不遷移、不計（與現行計費白名單一致） |

**反消耗／返還：** 點名結果由「計費（扣權益）」改為「不計費」（例如 no show → 病假／事假），或依既有反操作清除不應存在的計費列時，必須撤銷該次消耗，將額度加回**原** `pool_id`（事件見 §3.7 `entitlement_reinstated`）。對齊現行改點名／取消補堂 Confirm 路徑，禁止只改紙不改池。是否延長該池 `valid_to` 屬可選產品政策，不綁死在返還本身。

連堂＝2 堂、連堂單項補堂只計 1 堂等單位規則，沿用扣堂文件，不另訂。

### 3.7 營運事件類型（抽象同類、操作分型）

取消／請假／延期／補堂在抽象上皆為「改交付宣告與權益連結」；操作上必須分事件，並映射既有 `leave_makeup_records`／排程變更，**禁止**另造與現行無關的平行宇宙。

| 事件類型 | 對權益池 | 對宣告 | 對扣堂 |
| --- | --- | --- | --- |
| `class_cancelled`／老師請假取消原堂 | 不扣 | 原宣告 void | 無交付則不扣 |
| `class_reschedule`（全班改期） | 仍屬原池 | 原 void；新 schedule 建 active（繼承 pool） | 於新交付點名後依 §3.6 |
| `student_leave` | 依請假安排；事假／病假預填不扣 | 該日不應再當應到（或預填請假態） | 見扣堂文件 |
| `student_makeup`（個別調堂補回） | **仍屬原池**（不轉一期→二期） | 原日處理＋新 schedule 建宣告（繼承 pool） | 補回堂點名後依 §3.6 |
| `student_defer`（順延下一期） | 本期不消耗；改綁下一期包裝／池；宜**批次工具**，非逐堂人手 | 本期往後不自動宣告 | — |
| `student_transfer`（轉科／轉班） | 出舊池、入新池＋稽核 | 宣告改跟新命名空間 | — |
| `entitlement_reinstated`（權益返還） | 加回原池（對應曾扣的消耗列） | 通常不變；若宣告已因故 void 則依個案 | 撤銷該次消耗；見 §3.6 |
| `manual_roster_add` | 見 §3.8 | 必須建宣告 | 點名後依 §3.6 |

### 3.8 手動加名 workflow（禁止捷徑）

禁止直接寫入 `attendance_details` 繞過權益／宣告。保留緊急入口，但走完整路徑：

```text
手動加名
  → 檢查可用 entitlement_pool（命名空間相符、有餘額）
    → 有池：建立 attendance_declaration（active，記 manual_reason／操作者）
    → 無池：建立 pending_exception，不直接扣堂、不假裝有權益
  → 點名結果可暫存於已宣告者
  → 無池例外：後台審批 → 補權益後轉正式宣告，或駁回
```

例外狀態（暫定）：`manual_added_pending`／`manual_added_approved`／`manual_added_rejected`。  
須權限管控＋事後覆核報表。過渡期盤點所有直寫 `attendance_details` 的路徑並收斂。

**駁回收口（防白嫖）：** 若審批駁回時已存在交付事實（已點名計費或確認已上課），**不得**只把例外標成 `rejected` 結束。必須擇一收口並留稽核：

1. 補鑄權益（或確認池）→ 正式宣告 → 依 §3.6 消耗；或  
2. 記營運欠堂／跟進工單（對齊既有 `student_pending_lessons` 一類營運債，細則開工定）；或  
3. 明確作廢該次點名結果並說明（僅當確認並無交付）。

本階段**不**自動串門禁、**不**強制自動開立欠費發票引擎（欠費門禁另議；收款寫入口徑本階段不改）。

### 3.9 統一資格服務（入口約束）

所有產生「誰應到／可否加名／提醒對象」的路徑，最終只經同一服務層（名稱實作時定，例如 roster eligibility service），核心能力須覆蓋：

- 依 `scheduleId` 取已宣告應到名單  
- 查學生於某命名空間的權益餘額  
- 建立／void 宣告（含手動加名）  
- 依點名結果套用 §3.6 消耗與反消耗（返還）  
- 轉移權益（轉科／順延批次）

規定：點名紙、欠堂對帳、WhatsApp 提醒、班別學生相關名單、手動加名等，**不可**再直接用 period／date／`enrollment_period` 推點名資格。計糧是否讀同一來源另題，但不得反向用計糧規則定義點名資格。

### 3.10 資格 reason code（可解釋）

每個資格判斷須回傳穩定 reason code，UI 顯示短句，避免無名又人手改紙。

| code | 含義（例） |
| --- | --- |
| `eligible_declared` | 已宣告且池有效 |
| `not_declared` | 有／可能有權益但未宣告 |
| `no_entitlement_balance` | 命名空間下無餘額 |
| `pool_expired` | 池已過 `valid_to`（若有） |
| `namespace_mismatch` | 池與本堂班／學年包裝不符 |
| `schedule_cancelled` | 交付已取消 |
| `student_deferred` | 已順延 |
| `student_transferred` | 已轉出 |
| `manual_pending_approval` | 手動加名待審 |

例：「無法加入：有暑期第一期權益，但本堂屬正規班命名空間。」（`namespace_mismatch`）

### 3.11 過渡、日落與遷移閘門

| 項目 | 現行 | 要求 |
| --- | --- | --- |
| `makeup_of` → `enrollmentEligibilityDate` | 止血：補回堂沿用原取消堂日期判資格 | 新模型上線後廢止；不可無期限沉澱 |
| 單堂改掛 | 宣告層既有片段 | 終局納入統一宣告模型 |
| 所有產名單入口 | 未盤點齊 | 最終只經 §3.9 |

遷移分三步（開工同步寫死腳本與通過標準）：

1. **Shadow**：生成新池與新宣告，**不**影響正式點名紙；輸出差異（`old_roster_count`／`new_roster_count`／`missing_in_new`／`extra_in_new`／`reason`）。
2. **對照可讀**：班別／點名側可看舊規則 vs 新宣告是否出現及原因（reason code）。
3. **分批切換（2026-08-04 改定）**：**先正規 `2627`**（對齊「開始接受報讀」即啟用）→ 單堂與特殊補堂（同學年）→ **`26SM` 暑期不強制本輪切換**，維持舊路徑至日落。保留快速回退（舊查詢路徑按學年硬閘至日落）。切換前必須通過對帳報告；每個 R 風險對應驗證查詢（見 §3.12）。

**雙路徑約束（防「正式行為又新又舊」）：**

- 允許 codebase 暫存舊／新兩條查詢，但必須以 **`academic_year`（或同等 feature gate）** 切開：`26SM` 正式點名紙只走舊；`2627` 啟用後只走新。
- **禁止**同一堂／同一學年入口混用「日期推期數」與「宣告→池」作正式名單。
- 8 月 `26SM` 對前線應感覺零變化；新模型先服務即將開口嘅 `2627` 報讀。

### 3.12 對現有學生學費與權益（開工約束）

詳見 [`2026-08-03-summer-enrollment-tuition-rights-impact.md`](../audits/2026-08-03-summer-enrollment-tuition-rights-impact.md)。

- 守住不改收款／月費／收入認列時，點名修復**不應**變成加費或退費。
- 權益目標＝等價遷移＋修復跟堂；不應借機縮減已購堂數。
- 風險與防護：

| 風險 | 含義 | 防護（須齊備才切換） |
| --- | --- | --- |
| **R1** | 池初始化少鑄 | 初始化來源寫死；shadow 對帳「舊已付／應有堂數 vs 新池餘額＋已消耗」 |
| **R2** | 歷史排程未回填宣告 | 回填規則＋`missing_in_new` 報告為零（或僅含已解釋例外）才切班 |
| **R3** | 過早改消課／月結口徑 | **已禁止**本階段改動 |
| **R4** | 禁手動加名又無補救 | §3.8 緊急補宣告／pending exception |
| **R5** | 命名空間過寬或過窄 | §3.2 唯一鍵＋跨命名空間拒扣；抽樣跨期補回／轉科個案 |

開工閘門（2026-08-04）：產品方案已拍板；遷移與歷史回填規則開工時同步寫死；會計另案不擋第一期。**生效閘＝`2627` 開始接受報讀前**，新報讀須能鑄池，隨後有排程／點名時讀宣告。

### 3.13 現況帳本盤點（為何需要新方案）

**沒有**統一「學生還有幾堂」總帳；現為多本局部真帳，外加數套推導規則混充權益。

**真實帳本（約七本）**

| # | 帳本 | 主要落點 | 記載內容 |
| --- | --- | --- | --- |
| 1 | 收款 | `payments` + `payment_details` | 金額；收據 `lesson_count` |
| 2 | 月費應收 | `monthly_tuition_charges` | 某月應收堂數／金額 |
| 3 | 轉結餘 | `tuition_credit_entries` | 請假後可抵下月的金額／堂費結餘（不是可上課次池） |
| 4 | 消課／點名消耗 | `attendance_details` | 實際點名狀態 |
| 5 | 請假／調堂事件 | `leave_makeup_records` | 請假日、補回綁定、`tuition_disposition` |
| 6 | 待補欠堂 | `student_pending_lessons` | 遲報缺堂等營運欠堂 |
| 7 | 單堂掛堂 | `student_enrollment_sessions` | 單堂生綁定 `schedule_id` |

**假／推導規則（約五套）**

| 名稱 | 實際做法 | 問題 |
| --- | --- | --- |
| 報讀包裝當權益 | `enrollment_period` | 銷售 SKU，不是堂次池 |
| 日期推期數 | 排程日對 `academic_year_periods` | 跨期補回裂縫根源 |
| 追學費缺口 | 已繳堂數減計費點名 | 對帳差值，不是餘額帳 |
| 堂數缺口檢查 | 已繳減已綁排程減 pending | 啟發式檢查 |
| 交付日代理權益 | 看排程日期／補堂備註 | 交付不等於擁有 |

**七本真帳主路徑依賴（重構時對照震盪面）**

```
報讀／人手
  → (6) student_pending_lessons
  → (7) student_enrollment_sessions（單堂）
  → 包裝欄 student_class_enrollments（假權益）

收款
  → (1) payments / payment_details
       ├─ 可掛 → (2) monthly_tuition_charges
       └─ lesson_count 被對帳讀取

請假／調堂
  → (5) leave_makeup_records
       ├─ 轉結餘 → 寫 (3) tuition_credit_entries
       ├─ 影響 → (2) 月費減收／抵扣
       └─ makeup_schedule_id → 點名名單額外納入

點名紙
  → 讀：包裝＋日期推／(7)／(5)／makeup_of 止血
  → 寫：(4) attendance_details

排程 schedules＝交付層，不是權益
```

第一期實作應主要改「點名資格來源」並新建權益／宣告；避免同時改收款、月費、轉結餘的寫入口徑。點名寫入（尤其手動加名）必須與宣告／池一致。

### 3.14 支付／滾堂產品方向（2026-08-06 · 未正式簽核）

**已強化共識（方向）**

1. **全面用權益池滾堂**；日常營運**唔再**用「轉結餘」滾下月學費。  
2. **唯一池→錢**：學生退讀退款（非常少有；通常轉科代替）。  
3. **前台收款建議**：睇權益池 `remaining` ＋交費月份該生排程（邊個排程有呢個學生）；建議應收堂數 ≈ 該月排程堂數 − 池餘；**家長可多交／少交**（堂數可調）。  
4. **職責分開**：排程／到課宣告＝理論上應出現（除已請假等）；已付／剩餘＝睇池再處理。月中加減堂必須對照排程。  
5. 請假遲用：唔扣池；下月少收新堂（延續 08-05）；**遲用路徑唔寫轉結餘**。
