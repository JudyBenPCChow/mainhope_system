## 一、整體評價

`summer-enrollment-roster-consistency.md` 由最初嘅「暑期跨期補堂 bug report」進化成一份正規嘅 **domain model audit**，質素高。每輪迭代都挖得比上一輪深：

1. 第一層：兩套跟堂機制不一致（單堂改掛 vs 期數日期推）
2. 第二層：收費同點名根本行緊兩個唔同方案
3. 第三層（現版本）：四本帳模型＋7 真帳 5 假帳盤點

結論：**方向完全正確，可以作為產品定案嘅基礎文件。**

以下係逐節詳細意見。

---

## 二、做得最好嘅部份

### 2.1 現況帳本盤點（原文 §現況帳本盤點）

全篇最有價值嘅新內容。7 本真帳＋5 套推導假帳嘅盤點，係任何重構之前必須做嘅功課。核心發現：

> 「沒有一本統一『學生還有幾堂』總帳」
>
> 「收費行 B 直覺，點名行殘缺 A／日期推，兩套帳從未對齊」

呢個診斷精準過最初版本好多。之前只係話「兩套跟堂機制」，而家明確指出係**收費同點名兩個子系統行緊兩個互相矛盾嘅方案**——呢個先係 root cause，唔係單一 bug。

### 2.2 前線心態（原文 §前線心態）

> 「收咗幾堂錢，就應該嚟幾堂；改期唔改『有冇份』」

將前線直覺寫入 design doc 係好做法：
- 令產品決定有 user research 基礎，唔係憑空假設
- 提醒團隊：**如果系統同前線直覺相反，前線會繞過系統**（手動加名唔入帳就係後果）
- 為 B 方案提供咗業務直覺上嘅支撐

### 2.3 會計未清就唔好郁收入認列

> 「會計／每月收入／消課收入口徑：仍須另花時間思考，未定案前唔好當實作前提」

呢個克制係正確嘅。先 fix 權益＋到課宣告（頭三本帳），消課收入後搞，係合理嘅 phased approach。唔少團隊會喺權益模型未定案時就改收入邏輯，結果兩邊一齊爆。

### 2.4 約束個案表（原文 §必須支援嘅約束個案）

五個約束個案覆蓋咗核心 edge cases，尤其「請假／調堂／順延＝三種不同指令，禁止只改紙不改帳」呢句原則寫得好。任何方案過唔到呢五個情境就唔合格。

---

## 三、需要留意或補充嘅位

### 3.1 「B＋宣告」嘅定義要更強硬

原文話「傾向 B＋到課宣告」，但寫法有機會令人誤會「B 為主、宣告為輔」，即係揀 B 方案再加少少 reservation 就得。

**實際上：B（權益池）同到課宣告（Reservation）係 equally mandatory 嘅兩層，缺一不可。**

| 如果只有 | 結果 |
|---|---|
| 只有 B（純 pool） | 唔知邊個會出現喺邊堂點名紙（你之前指出嘅問題） |
| 只有宣告（殘缺 A） | 跨期補堂消失；退費對數冇 source of truth |

**B＋宣告 ＝ 唔係 B 嘅變種，而係 B（權益層）同 A（宣告層）嘅 mandatory 交集。**

建議原文明確加一句：**「B＋宣告」係兩層皆必須；權益層答『仲有幾多堂』，宣告層答『邊日嚟』。任何一層缺席都係 incomplete model。**

### 3.2 「到課宣告」層嘅實作本質上就係 A

呢點原文輕輕帶過但值得更坦白：

> 「方案 A 仍可做宣告嘅實作細節（預排時大量自動掛）」

實際上，宣告層嘅實作**就係**方案 A 嘅掛勾機制——只不過改用 pool 決定「掛唔掛得」，唔係用日期推。

即係：**你唔係揀 A 定 B，你係同時要晒兩樣。** 前線見到嘅（點名紙有名）係 A 嘅結果；背後決定「有冇權出名」係 B 嘅 pool 把關。

建議原文將呢個關係畫清楚，避免將來有人問「咁我哋究竟係行 A 定 B？」。

### 3.3 缺咗一個約束個案：多 pool 消耗優先序

五個約束個案已經好全面，但少咗一個：

| 個案 | 要求 |
|---|---|
| 學生同時有第一期餘額（2 堂）＋額外買單堂 package（4 堂），出席補堂時扣邊個 pool 先？ | 多 pool 消耗需有明確優先序（FIFO？pool 到期日近者先？手動揀？） |

呢個而家唔一定要答，但應該寫入約束個案表，否則將來 implement 到消耗邏輯時先發現，成本高好多。

### 3.4 手動加名嘅危險性要重點處理

原文提到「手動加名若保留，應變成補權益＋補宣告＋audit」，方向正確但未展開。

手動加名係成個系統最危險嘅 operation——佢 bypass 晒所有 guard。如果保留呢個功能（而睇前線習慣，一刀切刪除唔現實），強烈建議：

> **手動加名嘅 backend path 必須同「正式安排補堂」完全一致（create reservation → check pool → audit log），唔可以有第二條 code path 直接 insert attendance record。**

否則無論你 implement A 定 B 定四本帳，前線繼續手動加名落 `attendance_details`，所有 guard 都係擺設。

### 3.5 7 本真帳之間嘅 dependency 未畫

現況盤點非常強，但 list 出 7 本真帳之後冇講佢哋之間點互動（邊個 update 邊個、邊個 read 邊個）。呢個對重構好關鍵——改一本帳可能震到其他 6 本。

建議補充一個簡單文字 diagram，標明而家 7 本帳之間嘅 read/write dependency。唔使靚，但要準。

### 3.6 「兩期全報」喺結構因由表格中缺席

原文 §結構因由嘅表有三行：單堂、第一期／第二期、兩期全報。但兩期全報實際上係「包裝含兩期，點名機制同第一期／第二期一樣用日期推」。建議明確補充：**兩期全報生嘅點名機制同單期生一樣行日期推導，並冇因為包裝跨越兩期而有任何不同——因此同樣受跨期補堂缺人影響。**

## 四、對 A vs B 辯論嘅最終判斷

經過多輪討論，我嘅結論係：

**A vs B 嘅二元對立本身係問錯問題。** 真正嘅架構決定係：

> **你嘅系統要唔要承認四本帳各自獨立存在，各有各嘅 lifecycle 同 policy？**

如果承認四本帳，咁：
- **到課宣告帳**（點名紙有邊個）→ 實作上就係 A 嘅掛勾機制，呢個冇得避
- **權益帳**（仲有幾多堂）→ 實作上就係 B 嘅命名空間 pool
- **收款帳**（收咗幾多錢）→ 已有，keep
- **收入確認帳**（消課收入）→ phased，第二期先獨立

即係：**你唔係揀 A 定 B，你係同時要 A（for 宣告層）同 B（for 權益層），再加兩本已經有或將來要有嘅帳。**

Cursor 嘅四本帳 framing 比你最初問嘅 A vs B 更根本、更有用。A vs B 只係「到課宣告帳同權益帳各自點 implement」嘅 implementation detail。

---

## 五、對原文待做清單嘅補充建議

原文 §待做已經清楚，以下係額外建議：

1. **產品定案前**：先 confirm 四本帳模型係咪獲承認。如果只承認三本（押後收入確認），要明確寫低。
2. **過渡方案**：而家嘅 `makeup_of` 繼承止血方案，要 set expiry date（例如「暑期結束後廢止，由新權益模型取代」），否則會沉澱成 technical debt。
3. **手動加名 audit**：不論最終方案，應盡快對手動加名落 `attendance_details` 嘅所有 code path 加 audit log（哪怕只係加一行 log），作為過渡期嘅安全網。
4. **入口盤點**：原文提到「入口未盤點齊」，建議喺定案前做一次全面 grep——搵晒所有 produce 名單嘅 code path（班別詳情、欠堂對帳、WhatsApp 提醒、報表等），確保佢哋最終都行同一套 eligibility function。
5. **多 pool 優先序**：加入約束個案表，定案時一齊決定。

## 六、風險提示

| 風險 | 等級 | 說明 |
|---|---|---|
| 過渡方案沉澱 | 高 | `makeup_of` 止血方案如果冇明確 sunset date，會變成 permanent workaround |
| 手動加名繞過 guard | 高 | 前線繼續直接 insert attendance，四本帳模型形同虛設 |
| 會計討論無限期延遲 | 中 | 「另花時間」如果冇 owner + deadline，收入確認帳永遠唔會做 |
| 入口不一致 | 中 | 點名紙 fix 咗但 WhatsApp 通知／報表仲用舊邏輯，行政混亂 |
| 方案過度設計 | 低 | 四本帳模型完整但 implement 成本高；可以 phased，唔使一次過做晒 |

---

## 七、總結

`summer-enrollment-roster-consistency.md` 係一份好嘅基礎文件，方向正確，診斷精準。核心 insight「收費行 B 直覺，點名行殘缺 A，兩套帳從未對齊」已經值回票價。

主要建議：
1. **強硬定義 B＋宣告為 mandatory 兩層**，唔係 optional 配搭
2. **承認到課宣告層嘅實作就係 A 嘅掛勾機制**——你同時需要 A 同 B
3. **補充多 pool 消耗優先序**入約束個案表
4. **手動加名必須行同一 backend path**，唔可以有 shortcut
5. **畫 7 本真帳 dependency**，標明 read/write 關係
6. **set 過渡方案 sunset date**，避免沉澱

最後一句：**A vs B 係 implementation detail。真正嘅決定係四本帳模型認唔認，同埋邊啲 phased 做。**
