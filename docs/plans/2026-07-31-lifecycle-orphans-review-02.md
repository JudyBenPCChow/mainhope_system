## 🔴 發現 #1：審計函式變體未被列為階段 A 任務

**來源**：

方案「審閱定案」第 23 行明確要求：

> 刪出席路徑須用**會拋錯**的 audit 變體

方案「現況要點」第 94 行確認現有實作不滿足此要求：

> `logMgmtAuditAction`／`appendMgmtAuditLog` 現況失敗不擋主流程；**刪計費出席**路徑須另用可拋錯的 audit

**落差**：

階段 A 任務表（O1/O1t/O6/O2）中**沒有任何一項**包含「建立會拋錯的 audit helper」。這不是改一行 code——它需要一個新的 service 函式，與現有 fire-and-forget 的 audit 路徑分離。

**後果**：如果 O1-audit 沒先做，O1/O1t/O2 實作時只能用現有 `console.warn` 版本 → 直接違反審閱定案 P1-3。

**要求**：

請在階段 A 任務表新增一行，例如：

| ID | 內容 |
| --- | --- |
| **O1-audit** | 建立**會拋錯**的 audit 寫入 helper。**O1/O1t/O2 的前置依賴**——未完成此項前，不得實作任何刪除 attendance 的邏輯 |

## 🔴 發現 #2：O1t（試堂 lightweight）執行順序未展開

**來源**：

方案「審閱定案」第 26 行採納試堂 lightweight：

> 取消／刪試堂若已有該 schedule_id 出席 → 單一 Confirm「一併刪」（無「保留」三路）。改期掃舊堂，預設建議刪舊

**落差**：

O1t 的描述只有「lightweight Confirm」，沒有像 O1 那樣明確規範執行順序（掃描 → 樂觀鎖 → audit → 刪 attendance → 改/刪記錄）。試堂**改期**（`rescheduleTrialSession`，`schedule_id` 從舊值變新值）和請假改調堂是同一類問題，但沒有像 O1 那樣的變更矩陣。

**後果**：實作時可能變成簡單的 `confirmDialog` + 直接刪，跳過樂觀鎖和 audit（違反 P1-1 和 P1-3）。

**要求**：

請在 O1t 描述中明確加入執行順序，例如：

> 執行順序同 O1：掃描舊 `schedule_id` 出席（含 peers 如有連堂）→ 樂觀鎖 → audit 須成功 → 刪 attendance → 改/刪試堂。改期時掃舊堂出席，不可只彈 Confirm 就直刪。

## 🟡 發現 #3：`schedule_id IS NULL` 孤兒在階段 A–B 期間的風險敞口

**來源**：

審閱 #01 的 P0-2 建議 O1 掃描涵蓋 `schedule_id IS NULL` 的列。方案定案將此修正為歸 O5（階段 C）處理：

> `schedule_id IS NULL`（硬刪排程後）屬 O5／硬刪路徑，不是 O1 請假掃描主鍵能穩定找回的列

這個架構判斷是合理的（O1 無法用已消失的 key 掃描）。

**落差**：

但方案沒有明確寫出這代表的**時間差風險**：從階段 A 上線到階段 C (O5) 完成之間，如果有人硬刪了排程，那些 `schedule_id = NULL` 的 attendance **沒有任何工具能處理**，只能手動 SQL。

**後果**：上線後若出現此情況，會被當成 bug 回報，但其實是已知限制。

**要求**：

請在方案「刻意不做」或「審閱定案」章節加入以下聲明：

> `schedule_id IS NULL` 孤兒（排程硬刪後 ON DELETE SET NULL 殘留）歸 O5（階段 C）處理。階段 A–B 期間此類孤兒僅能手動 SQL 處理，屬已知風險接受，階段 C 上線前不視為 bug。
