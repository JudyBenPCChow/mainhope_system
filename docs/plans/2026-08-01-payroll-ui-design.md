# 計糧頁面 UI 設計建議

> 日期：2026-08-01  
> 參考產品：TutorCruncher、Teachworks、Classcard、Gusto、OnPay  
> 設計前提：六種薪酬模式全部系統內計算；計糧人員 = Christine/Mark（manager 角色）；每月一次

---

## 0. 競品分析摘要

### Teachworks — 最接近明學的模式

Teachworks 的計糧流程對明學最有參考價值：

- **以 lesson 為單位**：每節課自動帶入該老師的 wage rate，計糧人員**勾選**要計薪的課節，系統自動加總
- **Wage Tiers**：同一服務不同老師可有不同費率（對應明學 PT 專科班初中/高中/Judy 特別費率）
- **Non-Hourly Wages**：支援非時薪的薪酬項目（對應明學固定月薪、分成制）
- **Bulk Wage Payments**：一鍵支付多位老師
- **界面結構**：`Employees → Employee Hours` → 選日期範圍 → 每老師一行，可展開看明細 → 勾選 → 底部付款表單

### TutorCruncher — 分成制的參考

- **Split Payments**：支援按比例的薪酬分配（對應 Mark/Christine 的 60% + override）
- **Custom Pay Rates per Job**：每個 job（班級）可有獨立費率（對應 Sum/Cyndi 的獨立定價）
- **Tutor Dashboard**：老師可看到自己的 hours vs pay（明學可以不做老師端，但 manager 需要 internal view）

### Classcard — 手機端參考

- **Staff App**：計糧人員可在手機上處理 payroll（明學 mobile-first 策略的參考）
- **Attendance-based**：出席紀錄直接驅動計薪（與明學相同）

### Gusto / OnPay — 通用 payroll UI pattern

- **Payroll Run Wizard**：選期間 → 審核 → 確認 → 匯出
- **Anomaly Detection**：結算前自動標記異常（缺工時、金額異常變動、新入職未設定）
- **Color-coded Status**：Draft / Pending Review / Approved / Paid

## 1. 設計原則（明學專屬）

1. **自動計算，人手審核**：系統從 attendance/schedule/payment 自動算出每人薪酬。計糧人員的任務是審核異常、確認數字，不是人手輸入公式。
2. **結算前標記異常**：缺點名、HC 為零、金額異常變動（比上月 ±30%）、無費率配置 — 全部在確認前紅標，不等到出糧後才發現。
3. **月結 snapshot 不可變**：確認結算後 freeze 所有明細。日後費率變更不影響歷史。
4. **一次過處理全部老師**：20 人不需要分批。一個畫面看到所有人，異常的老師排最前。
5. **匯出即用**：CSV 格式可直接上傳銀行批量轉賬；PDF 糧單可發給個別老師（如需要）。
6. **手機可用**：計糧人員可能不在電腦前。至少審核和確認要能在手機完成。

## 3. 核心互動流程

### 3.1 每月計糧四步驟

```
Step 1               Step 2              Step 3             Step 4
┌──────────┐       ┌──────────┐        ┌──────────┐       ┌──────────┐
│ 選月份    │  ──▶  │ 審核數字  │  ──▶  │ 處理異常  │ ──▶  │ 結算匯出  │
│          │       │          │        │          │       │          │
│ 系統自動  │       │ 展開每老師│        │ 人手補數據│       │ 一鍵 CSV  │
│ 跑計算    │       │ 看明細    │        │ 或確認無誤│       │ freeze   │
└──────────┘       └──────────┘        └──────────┘       └──────────┘
   自動                人手                人手                系統
```

### 3.2 Step 1：選月份

- 預設本月。切換月份時自動重新計算
- 「重新計算」按鈕：如果中途有新點名／新報讀數據，可手動觸發重算
- 計算結果為草稿狀態，不影響任何歷史記錄

### 3.3 Step 2：審核數字

每位老師一行，預設收合。展開後顯示：

| 項目 | 明細 |
|---|---|
| 薪酬模式 | PT 專科 HC 制／固定月薪／分成制／… |
| 計算明細 | 逐節 breakdown（日期、班別、HC、金額） |
| 異常標記 | 紅點（缺數據／金額異常變動） |
| 總薪酬／MPF／實收 | 三欄數字 |

**Teachworks 的 checkbox 模式在明學不適用** — 因為明學計薪是「所有已點名課節自動納入」，不需要逐節勾選。勾選模式適合「不確定該不該計薪」的情境，明學的邏輯是：有 attendance = 計薪。

### 3.4 Step 3：處理異常

系統自動標記的異常類型：

| 異常 | 偵測邏輯 | 處理方式 |
|---|---|---|
| **缺點名** | 已排程但無 attendance record | 標記，等點名補齊後重算 |
| **缺費率** | `payroll_rates` 中無該老師的有效費率 | 需 alien 到設定頁補費率 |
| **HC 為零** | attendance 有記錄但 HC = 0（異常數據） | 需人手確認該節是否應計薪 |
| **缺工時** | Cody WFH 無本月 `payroll_manual_hours` | 人手輸入 |
| **金額異常變動** | 本月金額比上月 ±30% | 標記提醒審核（不阻止結算） |
| **功課班條件未達標** | Christine 功課班報名人數 < 12 | 提示該項為 $0（非異常，僅 FYI） |

### 3.5 Step 4：結算匯出

- 「確認結算」→ freeze 所有明細到 `payroll_snapshots`
- 狀態變更：草稿 → 已結算
- CSV 匯出格式：`教師名, 銀行帳號, 金額, 備註` — 直接上載銀行批量轉賬
- PDF 糧單（可選，第二期）：每位老師一頁，含薪酬 breakdown、MPF 扣除

---

## 4. 人手輸入點

計糧過程中，只有兩個地方需要人手操作：

### 4.1 Cody WFH 時數

- 位置：Cody 的展開明細行內，或獨立的小表單
- 輸入：月份 + 時數（decimal）
- 輸入後自動重算 Cody 的薪酬（$60/hr × 時數）
- 如果本月未輸入，Cody 行顯示紅標「缺 WFH 時數」

### 4.2 功課班工時覆寫（可選，備用）

- 正常情況：功課班工時 = attendance 節數 × 1.25hr，自動計算
- 特殊情況（例如老師出席了但系統漏記錄）：允許 manager 人手覆寫某老師的功課班總時數
- 覆寫後標記「人手調整」，與自動計算的數字並列顯示

## 5. 歷史查閱

`/Payroll?month=2026-07` 查看過往月份：

- 已結算月份：唯讀顯示，不可修改。附「匯出 CSV」按鈕（可重新下載）
- 草稿月份：可繼續編輯、重算、確認結算
- 如果該月尚未有任何計算記錄，顯示「尚未計算，點此產生」

## 6. 費率管理（子頁面或獨立 modal）

不適合塞在主計糧頁面。建議獨立路徑：`/Payroll/Rates`（僅 alien 可見）

- 每位老師的當前有效費率一覽
- 新增費率：選老師、選 rate_type、填 amount、填 effective_from（預設下月 1 日）
- 歷史費率：該老師的所有過往費率，含 effective_from / effective_to
- 不允許刪除，只允許「設失效日期」（soft close）

## 7. 權限

| 角色 | 可看 | 可做 |
|---|---|---|
| alien | 所有老師薪酬明細、費率管理 | 結算、修改費率、匯出 |
| manager | 所有老師薪酬明細（不含費率配置頁） | 審核、確認結算、輸入 Cody WFH 時數、匯出 |
| admin | ❌ 不可進入 `/Payroll` | — |
| teacher | ❌ 不可進入 | — |

| 現有頁面 | 關係 |
|---|---|
| `/MgmtDashboard`（營運總覽） | 首頁摘要顯示「本月計糧狀態」（已結算／草稿／未開始）＋總額 |

| `/PaymentHistory`（繳費紀錄） | 學費收入數據同源；計糧引擎讀取 payment 數據計算分成制 |

## 9. 實作建議

1. **先做 Step 1-3（計算＋審核），再做 Step 4（結算 snapshot）**：可以先在 SQL 驗證計算結果正確，再包 UI
2. **手機優先**：計糧人員可能用手機審核。列表和展開明細必須在手機上可用
3. **Golden test 驅動**：用規則文檔 §11 的數據建 SQL test，CI 每次 migration 都跑。確保計糧邏輯不會被其他改動破壞
4. **漸進增強**：第一版先做到「看數字＋確認結算＋匯出 CSV」。PDF 糧單、email 自動發送等可後加
